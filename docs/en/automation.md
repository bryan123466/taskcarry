# Scheduled governance in the original chat

[Three-step setup](windows-example.md) · [Feedback examples](user-feedback-examples.md) · [Technical contracts](../GOVERNANCE_API.md)

Standard setup establishes **two or three daily slots** in your original governance chat: one morning report and one or two absorption slots. Governance recommends a useful rhythm, then confirms your times and timezone. It reuses matching schedules, keeps the selected runtime/model/permissions and never creates another governance writer just to arrange automation. You retain the right to pause or explicitly use manual operation; that choice is recorded as a difference from the complete scheduled configuration.

## The two kinds of slot

| Slot | Work and user feedback |
|---|---|
| Morning report | Review selected current sources, facts, decisions, dependencies and health; continue authorized missing effects; check the official release channel and recovery coverage; save meaningful changes and deliver a concise report with necessary decisions and next work. |
| Absorption | Understand changed source revisions, retain evidence and judgments, update affected workbench views and verify consumption. No substantive change normally remains quiet. Necessary decisions or real failures can be surfaced without repeating already delivered questions. |

Each turn uses a bounded `cycle` with the original task, owner and exact resources. It distinguishes observed, understood, published and consumed, retaining an original continuation point if interrupted. Known issue/fix evidence is evaluated for applicability; recording a fix does not install it. Health needs recent evidence. Only real delivery receipts count toward follow-up on distinct dates.

Finding an official release does not authorize installing it. Private transfers use separately selected destinations and scope. This user-project schedule does not publish to the TaskCarry developer repository or silently dispatch messages to unrelated chats.

## Four evidence levels stay separate

| Evidence | What actually happened |
|---|---|
| Configuration readback | Every slot has the expected original chat, cwd, daily time/timezone, active state, fixed runtime and full prompt hash. |
| Natural trigger | The configured slot actually arrived at its scheduled time; a manual test is recorded separately. |
| AI execution | The original-chat AI read the relevant context, performed the authorized cycle and retained actual results. A delivered reminder alone does not prove execution. |
| Report delivery | The report actually reached its intended user location, with a delivery receipt. An internal result file alone is not delivery. |

TaskCarry prepares exact schedule plans; the host's native tools create/read them. Missing host support remains a concrete setup gap, not a hidden operating-system timer replacement. The environment must be available as required by its host. Current native tool visibility and actual execution determine acceptance; a prompt cannot grant permissions or wake AI by itself.

`complete_governance_ready` means required configuration, first-cycle and recovery checks passed. `natural_trigger_verified` requires all selected slots' actual triggers and execution; `closed_loop_verified` also requires complete governance readiness. Report slots include actual delivery. Awaiting the first natural trigger is not a failed run or grounds for fabricating evidence.

## Durable instruction for governance

> Continue this original governance chat using current project rules, its workbench view and original tasks. Reserve one bounded cycle with exact ownership/resources. Read only selected sources; understand revisions before updating facts, decisions and dependencies. Verify actual effects before resuming missing steps. Preserve professional instructions and WIP when publishing affected workbench entries, and distinguish publication from consumption. Check applicable issue/fix, evidence-qualified health, official release applicability and selected recovery coverage; do not install or upload without applicable authorization. Save meaningful local changes. In a report slot deliver the concise project report and record actual delivery; in an absorption slot stay quiet if unchanged. Preserve the original cycle and next step when waiting, do not revive completed history, and do not repeat necessary questions merely because the same day had another run.

The installed daily-governance Skill and `onboarding` schedule plan provide the exact profile-specific prompt. Use their generated prompt/hash for configuration, rather than treating the summary above as an acceptance receipt.
