# Update or continue your existing governance

[First installation](windows-example.md) · [Maintenance](governance-maintenance.md) · [Technical contracts](../GOVERNANCE_API.md)

## Identify what you already have

| Current situation | Continuation |
|---|---|
| TaskCarry is installed | Retain the original governance home, tasks and history. Assess the package, methods and project rules; update only applicable parts. |
| Another governance tool is in use | First inspect its rules, decisions, tasks and saving methods read-only, then confirm what to connect to TaskCarry. Preserve that tool and its data. Inheriting material does not upgrade, uninstall or automatically migrate the other system. |
| You only have a governance chat | Retain effective decisions and unfinished work while completing actual work locations, project memory, local saving and tool connections. Do not ask for the whole history again. If a separate governance directory is needed, retain the original conversation as a source. |

If unsure, send this in the original governance chat:

> Inspect our existing governance, tools and project work. Determine whether we need a TaskCarry update, continuation from another governance tool, or completed setup for an existing governance chat. Preserve effective rules, decisions, tasks, history and unfinished work without reinitializing an existing project. Follow the TaskCarry onboarding method you read, propose the smallest necessary continuation plan, guide the remaining steps and report actual results.

If you have a governance chat but no product, first obtain the package using the [first-installation folder preparation](windows-example.md). Governance reads the product entry under toolkit in its current working directory. If several state sources may apply, explain the difference before choosing; do not create another store to hide an unclear binding.

## Continue from another tool or an existing governance chat

Confirm the project and permitted reading scope before inheriting sourced goals, outputs, decisions, responsibilities and stopping points. State actual tool access and history coverage. When information needs transferring from an old window, provide the smallest handover prompt.

Governance then completes local Git, real work locations, connections to the same governance source, a first cycle, recovery verification and daily original-chat scheduling through the three-step method. TaskCarry package updates do not control the other tool. Any cross-system migration, deactivation or replacement needs its own concrete plan.

## Already installed TaskCarry: update in the original governance chat

Keep the original governance home and chat. To maintain TaskCarry, send:

> Check the registered official release source using my selected channel. If I supplied a package, verify its exact identity. Compare its notes with the actual runtime, installed Skills/methods and my project rules; explain applicable changes, compatibility and the smallest useful update. A discovered release is not permission to install it.
>
> Within my authorized update scope, preserve original control/source identities, tasks, checkpoints, facts, decisions, chats, custom configuration, Git index and unfinished work. Prepare an independent candidate runtime for a package change and retain a recoverable old installation. Preview exact managed-file/configuration changes; preserve customizations and verify every affected native connection.
>
> Evaluate the complete_governance profile complete_v1 against existing evidence. Retain earlier acceptance records with their original meaning; do not relabel them as the new profile. Reuse applicable evidence and complete the missing identity, sources, workbench consumption, first cycle, recovery rehearsal and daily-slot configuration checks. For legacy local-path identity, show an explicit identity plan before adoption, preserving its source alias and records. Do not initialize another control or merge business branches to refresh memory.
>
> Before changing schedules, retain existing valid bindings and review the exact one-report plus one-or-two-absorption arrangement with me; do not create duplicates. Natural triggering, original-chat AI execution and actual report delivery remain separately verified. After interruption inspect existing effects and finish only missing steps. Report what changed, what remains usable, verification results, exclusions and the next necessary action.

Governance checks the registered official channel during its routine. Offline means remote status is unknown; unchanged content requires no repeated maintenance. Stable and release-candidate channels follow your explicit selection. Same-version packages with different hashes require identity review.

Core updates, capability/method updates and user-project decisions are separate responsibilities. Public release, local installation, managed-file publication and a running host loading them are different receipts.

To resume: **“Continue the original TaskCarry update; verify already completed effects and finish the remaining plan.”** Read [release details](../RELEASE_0.2.0.md) for version differences, [feedback examples](user-feedback-examples.md) for expected results, and [manual fallback](manual-setup.md) only for the blocked step.

## Verify continuity during an update

Ask the original governance chat to verify existing tasks, decisions, sources and the latest checkpoint. In an independent candidate environment with authorized state copies, exercise project backup, manifest verification and restoration into a separate directory. Check selected artifacts and historical relationships; keep the restored replica in standby. If an explicit index upgrade is needed, verify preservation of original evidence. Users do not need to edit database markers or initialize another project.

Evaluate governance methods, project rules and the Core package separately. If a candidate is unsuitable, keep the verified runtime combination and name affected capabilities and next conditions. Unrelated governance improvements and specialist work can continue. Report package installation, managed configuration, native loading and actual local resolution separately. Rollback must retain facts added after switching; do not overwrite current records with an old database.

## What happens when a release is available

Governance explains the value for this project and prepares a concrete plan, then offers maintenance now, a later window or skipping this candidate. After confirmation it retains project memory and original work chats, verifying installation and native loading separately. See the [RC8 maintenance supplement](core-update-maintenance.md) for the procedure and a prompt for existing governance.
