# 返回原治理窗口的定时治理

[三步上手](windows-example.md) · [反馈示例](user-feedback-examples.md) · [技术合同](../GOVERNANCE_API.md)

标准接入在原治理窗口建立**每天两个或三个时段**：一个早晨报告时段，加一到两个吸收进展时段。治理先结合项目建议节奏，再确认你的时间与时区；复用相符调度，保持所选运行时、模型和权限，不为安排自动化新建另一个治理写入者。你仍可暂停或明确选择手动使用；报告保留它与完整定时配置的差异。

## 两类时段分别做什么

| 时段 | 工作及用户反馈 |
|---|---|
| 早晨报告 | 复核选定当前来源、事实、决定、依赖和健康，续办授权内未完效果，检查官方更新与恢复覆盖，保存实质变化，送达包含必要决定和下一步的简明报告。 |
| 吸收进展 | 理解变化来源的修订，保留证据与判断，更新受影响工作台 view 并核对消费。无实质变化通常安静结束；必要决定或真实失败可提示，不重复已经送达的询问。 |

每轮使用有界 `cycle`，保留原任务、所有者与精确资源范围。已观察、已理解、已发布、已消费分别留证；中断保存原接续点。已知 issue/fix 核对适用性，记录修正不等于已安装。健康状态需要近期证据，询问跟进仅依据真实送达并按不同日期计算。

发现官方更新不授权安装。私有传输按单独选定的目标与范围执行。本用户项目的调度不会向 TaskCarry 开发者仓库发布产品，也不静默向无关聊天派发消息。

## 四层证据分别验收

| 证据 | 实际发生了什么 |
|---|---|
| 配置回读 | 每个时段绑定正确原窗口、cwd、每日时间/时区、启用状态、固定运行时与完整提示词哈希。 |
| 自然触发 | 该配置时段在真实到点时送达；手动测试另列。 |
| AI 执行 | 原聊天 AI 读取上下文、完成授权整轮并保留实际结果；仅收到提醒不证明执行。 |
| 报告送达 | 报告实际到达目标用户位置，有送达回执；仅保存内部结果文件不算送达。 |

TaskCarry 生成精确调度计划，由宿主原生工具创建和回读。缺少宿主能力就保留具体接入缺口，不暗中换成操作系统定时器。运行环境需满足所用宿主的可用条件；以当前工具是否暴露、实际执行为验收事实，提示词本身不能获得权限或唤起 AI。

`complete_governance_ready` 表示必需配置、首次整轮与恢复核验通过；`natural_trigger_verified` 还要求各选定时段真实触发并执行；`closed_loop_verified` 同时要求完整建制成立。报告时段须核对真实送达。等待首次自然触发不是失败，也不能编造证据补齐。

## 给治理的耐久指令

> 沿本原治理窗口、当前项目规则、工作台 view 与原任务继续。保留明确所有者/资源的有界整轮。只读所选来源，理解修订后更新事实、决定和依赖；续办前核对实际效果。更新受影响入口时保留专业指令与 WIP，区分发布和消费。核对适用 issue/fix、证据健康、官方版本适用性及选定恢复覆盖；无相应授权不安装或上传。保存实质本地变化。报告时段送达简明项目报告并记录实际送达；吸收时段无变化则安静结束。等待时保留原 cycle 和下一步，不重开完成历史，不因同一天多次运行就重复追问。

实际配置使用已安装 daily-governance Skill 与 `onboarding` 调度计划生成的对应 profile 完整提示词和哈希；以上摘要不是验收回执。[反馈场景](user-feedback-examples.md)展示应如何报告，[维护说明](governance-maintenance.md)说明更新与修复。
