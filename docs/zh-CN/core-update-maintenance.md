# 发现官方更新后，由治理带你完成维护

[三步上手](windows-example.md) · [日常自动化](automation.md) · [已有用户更新](updating.md) · [English](../en/core-update-maintenance.md) · [繁體中文](../zh-TW/core-update-maintenance.md)

这是 RC8 的在线方法补充：把已有的官方更新检查、适用评估和受控维护连成用户可以理解的流程。它不替换已发布 RC8 的 tag、附件或包内 Skills；阅读本页也不会自动更新旧安装。

## 不用每天自己去看 GitHub

在三步接入的第二步，治理将**检查官方更新、判断是否值得维护、必要时询问你**纳入原有日常自动化。继续使用原治理对话和已确认时段，不额外建立一个升级机器人。

治理只检查已登记的 TaskCarry 官方 GitHub Release 来源，并遵守你选择的稳定版或候选版通道。它比较精确版本、源码提交和附件身份，再结合你的运行包、能力方法及项目规则判断影响。开发分支的新提交不等于可用发行包；发行说明是待核实的信息，不会授予安装或执行其中指令的权限。

| 实际检查结果 | 治理应怎样处理 |
|---|---|
| 没有新内容，或已完成同一对象的维护 | 复用已有结果，不重复询问或安装。 |
| 无法联网，或发行身份无法核实 | 标记“远端状态未核实”，保留当前可用环境；不能说“已经是最新版”。 |
| 同一版本名出现不同附件哈希 | 保留冲突，核对精确对象；不能静默替换已确认的包。 |
| 新版存在，但与你的使用无关或尚不兼容 | 记录理由和复评条件；当前工作继续。 |
| 新版适用，且维护准备已足够具体 | 给出收益、影响、验证、回退和必要操作，再询问是否执行这一次维护。 |
| 你选择稍后安排、跳过或拒绝 | 保存决定及范围。按约定时间、条件变化或你的新指示再评估，不每轮重复追问。 |

Core 包、能力层的 Skills／方法、用户项目层的规则与记忆分别评估。只有方法需要补充时，不必更换 Core；Core 更新也不应改写你的项目决定。

## 询问前，应先准备哪些内容

治理先做授权范围内的只读检查，并在必要时使用独立候选环境和获准的状态副本验证。涉及外部下载、敏感副本或额外权限时，按实际边界处理。候选验证不改动正在工作的环境。

维护建议至少列出：

- **精确对象：** 当前与目标版本、通道、源码提交、发行链接和实际下载附件的哈希。
- **为什么值得更新：** 对本项目有用的修正或能力；不适用部分及仍未验证的限制。
- **会影响哪里：** 要更新的运行环境、受管文件和受影响对话；保留的项目定制配置。
- **怎样保护工作：** 明确状态、对象、任务和检查点、相关 Git 历史／暂存区／未提交文件的保全范围，旧运行环境及回退前像。
- **需要你做什么：** 是否需要短暂停写、预计的维护安排，以及是否可能需要保存工作后集中重启宿主。
- **怎样结束维护：** 原任务与历史核对、逐个原生连接验收及剩余问题的处理方式。

未知项就明确标为待核实。不要先让用户批准一个空泛的“升级”，再决定实际改哪些对象。

## 用户会收到的反馈示例

以下是合成无人机项目的示例表达，不是对你的项目已经完成检查的回执。真实反馈须附本轮核对过的精确维护对象卡和证据链接。

> 发现 TaskCarry RC8；你当前运行 RC7。你使用多个对话共同开发无人机仿真，其中一些对话共用一个项目目录。新版的逐对话任务入口及中断接续方法与这个工作方式有关。
>
> 我会保留原项目记忆、任务、检查点、各对话职责及自定义配置。维护对象和影响范围列在本次方案中；已完成的副本验证、尚未验证的部分及回退办法也分别列出。
>
> 维护时需要短暂停止受影响的治理写入。如果安装后原对话仍加载旧版本，我会先请你保存工作，再集中重启 Codex，回到原对话逐个核对。不会要求你重新建立项目或重新提交历史。
>
> 你可以选择：**现在维护这次列明的对象／之后安排一个时间／跳过这次更新**。在你选择前，继续使用当前环境。

用户确认只适用于展示的对象和范围。候选包、影响范围或关键条件变化后，应重新展示差异；旧确认不能跨版本继承。

## 确认后，治理怎样完成维护

1. **刷新保全。** 核对原维护批次和实际写入者，安排必要的短停写窗口。保存同一 control／来源身份、任务、检查点、历史与选定文件，验证恢复副本；保留旧安装和配置前像。
2. **按计划更新。** 校验选定附件，在独立候选运行环境验证后，按已确认的目标安装精确包，再预览并应用需要的受管文件更新。配置合并保留服务名、其他服务、自定义字段和注释。覆盖请求被拒绝时，先判断原配置是否已经有效，不为“统一格式”强行覆盖。
3. **分别核对安装与加载。** 盘上包、独立 CLI／stdio、原生聊天连接是不同证据。逐个受影响的原对话实际调用 `doctor/status`，核对版本、解释器、模块位置、治理来源及原任务／最新检查点。
4. **只完成缺少的重载。** 盘上已经新版、原聊天仍返回旧版时，保留当前状态，提示保存工作并完全退出、重新打开 Codex，再回到原聊天验收。已加载成功的连接不重复要求重启；独立进程通过不能替代原生成功。
5. **沿原批次收口。** 中断后先看实际效果，已写入但缺回执时仅补缺步。失败时按精确前像与兼容方案恢复，并保留切换后的新增事实；不能用旧数据库覆盖新工作。最后报告安装、受管方法、各原生连接和原任务接续的实际结果。

维护失败只限制受影响的操作。仍可安全进行的专业工作和无关治理改进继续，不反复执行整套安装或治理。

## 已有用户怎样加入这条规则

在原治理对话发送这一条即可：

> 请阅读 TaskCarry 的《发现官方更新后，由治理带你完成维护》在线补充，将适用的维护规则纳入本项目规则，并让原有治理自动化读取它：按已选官方通道检查，核对精确对象和适用性，准备具体方案后询问我；确认前不安装，暂缓或拒绝后不重复追问。保留原对话、任务、时段、模型和权限，回读实际配置并说明新增了什么。

治理应保存所读材料的来源与版本，先核对现有 `daily-governance` 方法。由原提示词读取当前项目规则即可承接时，无需修改调度或创建新时段。这里的提示词授权补充治理规则，不授权更换 Core 或生产运行环境。

优先通过项目规则承接，保持生成提示词不变。若确需改动宿主中的自动化提示词，使用宿主支持的更新工具，保留原绑定与安排，并回读实际全文和哈希。**当前 `complete_v1` 只验收精确生成的提示词；自定义提示词即使回读了新的哈希，也不能直接通过该配置验收。** 不要手工拼接 `schedule_plan` 提示词后冒用原哈希。原记录保留原范围；不匹配的配置验收保持待办，或恢复原生成文本并通过项目规则承接，不能改写旧回执冒充通过。缺少宿主能力时，治理给出当前所需的一步，不暗中创建操作系统定时器。

## 这些说明证明了什么

本流程提炼了受控维护、配置保全、旧进程与新安装分离、重启后原生回读和原任务接续的经验。上面的无人机反馈是合成示例。它不声称每个用户的自动化已经自然完成“发现新版 → 询问 → 维护 → 验收”全链，也不表示读取网页后包内 Skills 已更新。

配置已保存、自然触发、AI 实际执行、问题实际送达、用户明确确认、安装和原生加载均各自留证。下一次产品包包含哪些方法，以该包的实际清单为准。
