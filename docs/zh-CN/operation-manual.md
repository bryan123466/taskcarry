<a id="onboarding"></a>

## 推荐的一条接入路线

为现有项目建立独立治理窗口，已有有效 TaskCarry 治理窗口/control 则复用。发送[一条接入提示词](windows-example.md#install)，由治理继承项目上下文、安装或复用工具，并带领完成剩余连接；用户不必先决定技术 ID 或专业窗口数量。

治理与记忆是默认职责。首次项目梳理帮助接入；临时或长期项目协调由用户选择。继续直接在原主窗口或专业窗口工作，调整协调偏好时保留同一记忆与任务身份。新增专业窗口可以为零。

助手读取获准的相关证据，说明缺失历史；候选理解与建议不替代已确认的有效决定。空治理目录不代表新业务项目，历史成果与 WIP 保留在实际位置。

## 谁负责什么

| 对象 | 职责 |
|---|---|
| 用户 | 项目方向、业务决定、验收及需要授权的动作。 |
| 治理窗口 | 维护项目记忆与证据，复核已接入进展，按计划接收明确阶段；按选择兼任项目协调。 |
| 工作窗口 | 读取相关有效决定、推进任务、保存有意义的进展并精确交付稳定阶段。 |
| 接收基线 | 用于接收阶段的独立干净 Git 工作区，不混入专业 WIP。 |
| TaskCarry 引擎 | 持久记录、核对条件，执行已支持的保存、接收、采用与恢复操作。 |
| 宿主 | AI 理解、实际聊天读取/创建、配置加载、权限与原生定时能力。 |

每个任务和写入范围保留一个主要写入者；其他窗口可只读复核或承担明确不重叠的子任务。聊天分开不等于工作区已隔离，调整前检查真实归属与活跃写入者。

<a id="continuation"></a>

## 一次完整盘点与日常接续

工作窗口接续前读取当前任务、相关最新检查点和有效决定；在有意义的成果、决定变化或暂停处，保存任务所属的选定文件、发现、来源和下一步。治理用这些记录维护共同理解，只补读有变化或缺失的相关上下文。旧聊天访问能力另行核对，没有自动全历史监控。

用 `facts` 保存带来源身份的决定与关系，保留原始陈述、证据和单独标明的 AI 判断。显式修订保留先前有效事实，并指出受影响工作；它使用同一 Core 状态，不建立竞争数据库，也不静默改掉原任务身份。

<a id="chat-continuation"></a>

### 原聊天无法继续时

不必预先建立空白备用聊天。原窗口持续报错或无法接续时，先让治理核对原任务、已保存决定、检查点、成果与未提交改动，检查中断前的操作是否已生效，并确认旧窗口及其后台写入已停止。若无法确认，新窗口先只读核对。

需要替换窗口时，治理给出同一项目和实际工作目录下的新聊天接续提示，保留原 control 与 `task_id`，登记新聊天的真实身份。新窗口自己调用原生 MCP、读取当前任务和工作台入口，复述已完成、尚缺及下一步，通过核对后只继续缺步。旧聊天作为历史保留；若恢复使用，先读取移交决定，避免两边同时写同一任务。治理窗口本身被替换时，另外核对定时任务的原聊天绑定，不自动复制调度。

此流程接续已保存且可核对的项目工作，不修复宿主压缩错误，也不承诺找回未保存或无法读取的内容。具体反馈见[原聊天故障示例](user-feedback-examples.md#chat-continuation)。

<a id="evidence"></a>

### 理解每种结果证明什么

| 情况 | 相应记录或操作 |
|---|---|
| 旧成果已在可信基线中 | 保留来源与纳入事实，不再次排队。 |
| 未完成或未提交工作 | 保存 checkpoint 和准确接续点，不称为交付。 |
| 稳定、明确的 Git 阶段 | 核对 base、commit、任务和完整路径，先预览接收计划再执行。 |
| 原有普通资料 | 保留选定文件与来源；后续工作窗口仍完成标准 Git 配置。检查点不提供通用非 Git 交付/接收。 |
| 暂停、等待或未变化任务 | 保留当前位置，不制造提醒或新积压。 |
| 任务确需已接收代码 | 按实际依赖预览采用，保留本地提交/index/worktree/新文件；只读取进度无需合并。 |
| 操作中断 | 核对实际效果和原身份，补齐支持的缺步。 |

地图和说明描述项目，工具记录与实际文件证明效果。保存、交付、接收、采用和业务验收分别判断，记录材料路径也不等于已验证备份。

<a id="move-project"></a>

## 换电脑或换 AI，继续原项目

在准备接手的电脑或 AI 工具里打开 TaskCarry 管家对话。如果要由这里统筹整个项目，可以这样说。

> 我想把原本在〔另一个 AI 或另一台电脑〕上的〔项目名称〕集成治理迁到这里，由你接任集成管家。请在本地重建原来各条工作线需要的环境，让我知道每条线做到哪里、接下来在哪个对话继续。

你也可以让新管家接任整个项目，同时指定「本机只重建〔开发〕和〔验收〕两条工作线，其他对话继续在原处工作」。如果只想转来部分工作，并保留原集成管家，可单独这样说。

> 〔项目名称〕继续由原管家统筹。这次只把〔工作线名称〕迁到这里，请帮我接上它的资料、进度和工作对话。

新管家根据你授权共享的项目文件和记录，核对各线分工、已采用的版本及下一步，协助把相应任务接到本地工作对话。缺少交接资料或需要你登录、开窗口时，它会告诉你具体要做哪一步。迁移集成治理时，先看新管家核对出的结果。你确认后，它会核实原端已停止主写，再正式接任。[跨机恢复与交接说明](remote-and-multicomputer.md)

## MCP、CLI 和定时治理的区别

MCP 让宿主 AI 直接调用内核动作；原生工具不可用时，固定运行时的隔离 CLI 继续绑定同一 control。两者均无需另配模型服务。接入文件生成、宿主加载与原生 doctor/status 调用分别提供证据，各工作台核对自己的实际包来源与绑定。

Windows Codex 新连接的操作顺序是：按治理给出的准确原目录，用 **Ctrl+O／打开项目文件夹**完成打开与信任；待治理核对配置和原聊天的项目关联后，保存工作，**退出并重新打开 Codex 一次**，返回原聊天逐窗验收版本、control、原任务与最新检查点。已经原生验收通过的连接不重复重启；其他宿主按其支持的方式加载。详细步骤见[接入与重启](manual-setup.md#mcp)。

已登记工作台的 setup 可将四项 Skills 和接入材料写到宿主工作目录，仍绑定原 control。共享目录使用 `binding_mode: "directory"`，提供 `target`、`workspace` 并省略 `task_id`；已有单任务绑定沿用默认 `task` 模式，同时提供这三项。两种模式都按既有登记核对，不初始化第二 control。生成片段用隔离 UTF-8 启动固定选定包，合并生效配置时保留它；详见[手动绑定与验收](manual-setup.md#mcp)。

## 完整治理与原任务接续

`complete_v1` 清单包括持久项目/副本身份、选定来源的理解、实际任务/工作区/Git 绑定、每个窗口原生连接及准确工作台消费、本地治理 Git、首次有界整轮、独立恢复演练、官方更新检查，以及每天两个或三个原窗口时段。这些是标准建制内容；私有远端、网盘和长期项目协调仍由用户选择。历史参考对话保留来源证据，不虚构活跃工作区。

用 `context` 读取原任务和当前 checkpoint，用 `facts` 保留带来源身份的决定与关系，将证据和 AI 判断分开。`cycle` 保留准确所有者/资源、计划效果、实际回执、来源阶段、健康和下一步。`source_scan` 只分页枚举授权本地元数据；正文由宿主另行读取。精确参数集中在[治理 API](../GOVERNANCE_API.md)。

`workbench` 冻结带来源版本的 view，生成准确私有入口计划后发布，保留 Git HEAD/index 和无关 WIP。核对当前指针、原任务/窗口与来源是否变化；发布、复核过的消费证据、原生 doctor/status 分别成立。来源已经变化的旧 view 不能当当前事实。

`recovery` 按选定范围捕获一致项目集、验证字节并在独立目录恢复为 standby。恢复回执列出 `disabled_host_files`：原宿主配置保留为证据，暂不作为恢复目标的活动配置，按新机器重新生成后再用。原项目身份加新副本身份不授权双写入；明确移交和真实原生验收后才激活。[恢复参考](remote-and-multicomputer.md)区分本地捕获、传输与真实第二宿主证据。

旧记录保持可读。`identity plan/execute` 显式采用可迁移项目身份并保留旧来源别名，不暗中合并另一项目；`upgrade` 单独维护派生索引。旧验收保留原 profile，新完整建制复核复用适用证据、补真实缺口，不改写旧历史。
