# 用户反馈示例：从零散对话到共同项目记忆

[三步操作手册](windows-example.md) · [无人机治理实例](../../examples/vision-drone-governance/README.md) · [三层架构](architecture.md) · [English](../en/user-feedback-examples.md) · [繁體中文](../zh-TW/user-feedback-examples.md)

下面用“图像识别避障无人机”说明各阶段应收到什么反馈。你之前已经分别讨论软件、算法和硬件，接入后希望这些工作依据相同决定继续推进，并按需要增加产品与推广职责。

**以下是合成情境中的反馈示意，不是安装成功回执。** 真实回答必须引用当次读取、配置和验证结果，不能复制示例就宣称通过。[独立实例](../../examples/vision-drone-governance/README.md)提供项目材料、完整过程及验证范围；无人机实物、飞控、飞行安全和市场效果没有因治理建制而得到验证。

## 1. 先看到候选项目，再选择读取范围

> 我已读取当前宿主可访问的对话索引。活跃和归档索引分别列出覆盖情况；仍有下一页或访问失败的部分会保留。这里的“已盘点”只覆盖列出的来源，不包括其他账号、设备或不可见聊天。
>
> 按标题与目录线索，我建议先确认：
>
> 1. **图像识别避障无人机**：包含已有软件、算法和硬件对话，是否属于同一个项目还请你确认。
> 2. **自定范围**：你也可以选择其中几段对话，或补充遗漏的项目。
>
> 目前只是候选分组，还未读取这些对话的正文。请告诉我要接入哪个项目。

如果用户已明确给出项目范围，治理可直接确认该范围，不必重复盘点无关对话。标题不足以判断的内容标为待确认，不能把名称相近当成业务关系已建立。

## 2. 选择后，收到有来源的项目理解

> 你选择了无人机项目。我已按确认范围读取相关历史，并将结论关联到原对话和材料。
>
> 当前目标是先形成图像识别避障方案与可复现的演示材料。软件、算法和硬件已有成果继续使用；尚未明确的参数保留待确认，不写成既定规格。
>
> 建议继续保留三个原工作窗口。等方案边界清楚后，可增加一个产品与推广窗口，整理目标用户、演示脚本和对外表述。它是职责建议，可以由现有窗口兼任，不要求你一定新增第四个窗口。

真实项目的目标和决定应来自读取内容或用户确认。这段描述仅展示表达方式。若历史只读到一部分，治理应同时说明实际页数、范围及尚未读取的内容。

## 3. 接入提示词已经填好，用户只需在指定位置发送

治理给出的是面向每个窗口的**接入卡片**，包含原对话、真实工作目录、任务职责、同一治理来源、完整提示词和预期反馈。它应填好自己已经核实的信息，不让用户手抄任务 ID、解释器或配置片段。

下面是原算法窗口会收到的提示词语气示意；真实交付还需附带该窗口的实际接入位置：

> 继续本窗口原来的无人机视觉算法任务。读取治理为本窗口发布的当前入口，核对原任务、最近检查点、工作目录与原生 TaskCarry 连接。保留原算法方案、未完成比较和本地改动。
>
> 本阶段与软件、硬件共用已经确认的输入和验收边界。请回报你实际读到的决定、仍缺的输入及下一步；若入口或连接未加载，说明具体缺项并继续不受影响的工作。

未挂在项目下的活跃对话先核对真实工作目录与工具，优先保留原聊天和历史，并按宿主能力关联同一目录。不能仅凭这个标签判断 MCP 不可用。若仍缺信任或加载，治理只给当前必要操作，随后回到原窗口验收；发送提示词不改变目录，也不能代替真实 MCP 调用。

<a id="open-existing-project"></a>

### 需要你打开原目录并重启 Codex 时

以下假设治理已核对原算法聊天使用合成目录 `C:/TaskCarry/workspaces/drone`，连接配置也已准备好。**这是已填目录的操作示例，不是让你建立这个目录。** 实际接入卡片应填你的原目录：

> 我已为原“无人机视觉算法”聊天准备连接。当前需要让 Codex 打开并信任它原来使用的目录，以便加载其中的 MCP 配置：
>
> 1. 在当前 Windows Codex 按 **Ctrl+O**；其他界面使用“打开／添加项目文件夹”。
> 2. 在文件夹选择框中选择 `C:/TaskCarry/workspaces/drone`，打开这个已有目录。此时**不用新建聊天、复制文件或建立另一份治理**。
> 3. 若出现信任提示，确认提示中是上述目录后允许。
> 4. 回到这里回复“已打开指定目录，并确认信任提示”；若未出现信任提示，请告诉我。
>
> 接下来我会按宿主支持的方式将原聊天关联到这个项目，保留历史和任务，核对它实际工作的目录仍是原位置。等本次所有目录的配置和关联都准备好后，我会告诉你可以集中重启，不需要每个目录重启一次。

如果新连接还没有加载，治理确认准备完成后继续给出：

> 原聊天与项目的关联已经核对，配置也已准备好。现在需要让 Codex 重新加载连接：
>
> 1. 先保存正在进行的工作，**退出 Codex，再重新打开应用**。
> 2. 在侧栏回到这个**原治理聊天**，回复“已重启”。不用重新安装，也不用新建对话。
> 3. 回到原“无人机视觉算法”聊天，发送：**“请使用本窗口 TaskCarry 原生 MCP 调用 doctor 和 status，核对实际版本、运行路径、control、原算法任务与最新检查点；读取并核对当前工作台入口，将实际回执交回治理。保留原身份、历史和成果继续。”**
>
> 我会分别核对各原窗口的实际回执，确认它们读取的是同一份治理记忆下各自的任务。已验收成功的连接不会要求你重复重启。

这段操作把原聊天归到其项目并加载连接，保留同一份治理和原任务。治理核对关联和实际工作目录，再由原窗口给出原生 `taskcarry_doctor`、`taskcarry_status` 回执。版本、来源、control、原任务与检查点匹配后才报告已接入；侧栏出现项目下的聊天或重启完成不等于验收通过。同目录的其他聊天仍分别核对各自任务与入口，不重复创建项目。

### 多个原对话共用一个目录时

以下仍是**预期反馈示例，不是现场验收结果**。假设核对后发现三个原对话都在同一个已有业务目录，以下用 `drone/` 表示：

| 原对话 | 保留的原任务 | 实际工作目录 | 接入安排 |
|---|---|---|---|
| 无人机软件 | `drone-software` | 已有 `drone/` 目录 | 使用该目录的共用连接，读取自己的软件任务入口。 |
| 视觉算法 | `drone-vision` | 同一目录 | 复用相同 MCP 与 Skills，读取自己的算法任务入口。 |
| 硬件方案 | `drone-hardware` | 同一目录 | 复用相同 MCP 与 Skills，读取自己的硬件任务入口。 |

> 三个原对话都保留，我会按这个已有目录准备一套连接材料。你不需要为了接入分别建立三个目录或三个新对话。各窗口继续自己的原任务，原生连接与共同记忆的实际读取仍逐个核对。
>
> 另一个只讨论过早期选型的旧对话可以仅作为历史来源，保留引用，无需给它安装 MCP 或建立 Git。若三个活跃窗口之后会同时修改冲突的文件或 Git 状态，再讨论是否需要独立工作树。

共享配置不代表共享任务身份。治理把每个真实聊天与原任务对应，未知聊天先核对绑定，不会默认采用目录中的第一个任务。

## 4. 共同决定改变时，各职责收到各自需要的变化

假设用户随后确认：“首个里程碑只做离线图像回放与模拟避障决策，暂不进入实机飞行。”

| 原工作职责 | 治理整理出的影响 | 该窗口继续做什么 |
|---|---|---|
| 软件 | 首阶段输入改为回放资料；不声称已经联通飞控。 | 整理图像输入、识别结果和避障决策展示的接口。 |
| 算法 | 根据同一组回放样例比较识别与决策结果。 | 保留算法比较和失败样例，列明模拟的局限。 |
| 硬件 | 提供方案约束与待验证条件；暂不开展飞行集成。 | 整理相机、计算与连接需求及尚未选定的项。 |
| 产品与推广 | 演示说法限定为方案与模拟能力。 | 准备产品说明和演示脚本，不把模拟写成实飞验证。 |

> 我已记录你确认的新里程碑及其替代的旧范围，保留原讨论作为来源。接下来的工作台入口分别呈现每个职责需要知道的变化；入口已发布与各原窗口已读取会分别记录。
>
> 你仍可直接在原窗口推进，不必把每个动作都交给治理批准。涉及共同边界的新决定会继续汇入项目记忆。

## 5. 最后收到可核验的完成报告

报告应使用当次真实结果，常见表达如下：

> **项目理解**：已整理目标、有效决定、各项成果和未完成位置；未确认的条件单独列出。
>
> **工作窗口**：逐个列出原窗口、职责、任务、实际目录及连接结果。只有拿到该窗口的原生回执，才写“已接通”。
>
> **保存与恢复**：说明本地 Git 实际保存了哪些文件，恢复演练覆盖了哪些状态、产物和历史；只登记位置的材料另列。
>
> **日常治理**：列出你确认的报告与进度整理时段、时区和实际配置读回。官方更新已检查时写明结果与适用判断；离线时明确仍未核实远端。
>
> **待办**：比如某窗口尚需重载，只给该窗口的重载和回读步骤。标准项目未齐，不写“全部配置完成”。
>
> **自然触发**：尚未到点时写“配置已读回，首次自然执行待验证”；真正触发后再补原 AI 执行、保存和报告送达证据。
>
> **下一步**：软件完善回放接口，算法整理比较，硬件明确约束，产品与推广准备与证据一致的介绍。你可以直接回相应窗口继续。

这份报告不会因为新建了几个文件就宣布整套治理已完成，也不会因为首次自然触发仍在等待而要求重复安装。

## 6. 接续和更新时，用户仍只需说当前目标

- **中断后：** “继续剩余配置。” 治理先查既有计划与实际效果，只补缺步。
- **保存工作：** “先保存这里，下次继续。” 原任务保留检查点、成果位置和下一步。
- **发现新版：** “判断这次更新对我的项目是否有用。” 治理比较 Core、能力方法与项目规则，给出适用建议和必要操作。
- **来自其他治理工具：** “接续这些规则和决定。” 治理先识别来源与范围，保留原系统，不把继承内容冒称为升级了第三方工具。

## 7. 算法聊天无法继续，新窗口接续原任务

以下是**预期反馈示例**。假设原算法聊天持续报错，项目文件仍在，空帧处理已有验证，而同帧多目标比较尚未完成。治理应先检查实际效果和旧窗口是否仍在写入，再给出这样的接续安排：

> 已保存的算法方案、空帧测试结果和原任务检查点都在。我已核对中断前的实际文件效果，确认旧窗口没有继续写入。同帧多目标比较仍未完成，因此不会重跑已经完成的空帧工作。
>
> 不需要提前准备备用窗口。现在可以在原算法项目和同一工作目录中新建一个接续聊天。我会准备已填好原任务、入口与下一步的提示词，记录新聊天的实际身份；原聊天和历史保留。
>
> 新窗口先调用自己的原生 MCP，核对同一治理来源、原算法任务及最新检查点，再读取项目决定和相关成果，回报“已继承什么、还缺什么、下一步是什么”。核对一致后，它只继续同帧多目标比较。
>
> 如果旧窗口恢复，请先让它读取这次移交决定，保留历史参考，避免与新窗口同时修改原任务。不能读取的旧内容或尚未保存的想法会列为缺口，不假称已经找回。

实际报告必须分别给出旧写入者停止的依据、新窗口原生读取回执和继续完成的产物；单纯创建新聊天不代表接续成功。这项能力保留项目工作，不声称修复 Codex 自身的压缩或聊天故障。
