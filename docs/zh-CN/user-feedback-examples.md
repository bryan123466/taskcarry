# 用户反馈示例：USB 数据采集与曲线显示工具

[三步操作手册](windows-example.md) · [三层架构](architecture.md) · [English](../en/user-feedback-examples.md) · [繁體中文](../zh-TW/user-feedback-examples.md)

假设你已在 Codex 中开发一个小工具：设备通过 USB 串口发送读数，电脑显示曲线并导出 CSV。你已有固件、电脑软件和仿真验证的工作对话，还有一份旧的硬件与接口讨论。TaskCarry 要把这些工作接在同一份项目记忆上，让各窗口知道共同约定和下一步。

**下文对话是合成的产品反馈示例，不是你的项目或某个宿主已通过验收的报告。** 随包提供的[可执行模拟资料](../../examples/complete-governance/README.md)可验证文本解析与数据回放；它没有连接真实设备、烧录固件或绘制实际用户界面。真正报告须引用当次证据，不能照抄示例中的成功结论。

## 先把项目说清楚

本例先约定 UTF-8 文本一行一帧：`READ,42,1000,1.234`，行尾为换行符。它依次表示“读数”、序号 42、模拟设备时间 1000 毫秒、模拟值 1.234。第一阶段先把“生成数据 → 解析 → 曲线显示 → CSV 导出”串起来，再验证断开和重连；无线连接留待后续。

| 专业职责 | 这阶段要做什么 | 怎样看出完成 |
|---|---|---|
| 固件与协议 | 确认字段含义，提供稳定的模拟读数与文本帧 | 给同一份输入，接收方能够按共同格式复现结果；尚不表示板卡固件通过测试。 |
| 电脑软件 | 解析帧，把读数送入曲线，并导出 CSV | 输入三帧，曲线对应三个点，CSV 的序号、时间和值与输入一致；实际界面和文件操作需各自验证。 |
| 仿真验证 | 回放正常、断开、重连 | 正常值可核对；断开不产生假数据；重连不重复旧点、不接上断开前的半帧。 |

这是三种职责，不要求每个用户必须开三个专业窗口；已有窗口可以合并承担。旧硬件说明只是读取来源，不因此宣称它是已接入的活跃窗口。真实采样、驱动、USB 时序和测量准确度仍需实物测试。

## 1. 总控先说明理解与接入范围

> 我理解你要做的是一个 USB 数据采集与曲线显示工具。第一阶段先用模拟数据跑通链路：固件侧提供约定的读数帧，电脑侧解析、显示并导出，验证侧检查正常与中断恢复。
>
> 我看到你已有固件与协议、电脑软件、仿真验证的工作对话，建议保留它们；如果目前只有两个窗口，可以把协议与仿真放在同一窗口，不必为了安装而拆分。旧硬件与接口讨论只作为参考来源。这个范围以你选定的对话和材料为准。
>
> 我会保留“先模拟、再接实物”和“本阶段不做无线连接”的有效决定。你仍可直接在专业窗口推进。我负责记录决定、核对依赖，并把共同协议的变化送回相关窗口；长期项目协调由你选择。

如果只是看到了标题和目录，总控应明确说“这是候选范围，还没读到具体内容”。选定范围后再读取正文；宿主没有读取对话的工具时，改用原窗口给出的最小交接，不把目录扫描当作已经理解项目。

## 2. 接入后给出能继续做事的安排

> 选定的工作窗口已连接同一治理。原任务、文件、未提交改动和专业说明都保留了，各窗口分别核对了自己的实际连接与当前入口。
>
> 共同数据格式已经明确，但电脑端的曲线与 CSV 还没有完成验证。下一步请固件与协议窗口保存稳定的三帧模拟输入；电脑软件窗口用这份输入接通解析、曲线和导出；仿真窗口先检查正常数据，再做断开与重连。接口旧笔记保留为参考，没有被登记成新工作任务。

这里应该看得到“谁继续什么、用什么材料、怎么验证”。配置好了治理，并不代表上述工程任务已经做完。

## 3. 第三步的完整配置报告

以下示例假设必需配置、第一次治理和独立恢复演练均已实际通过：

> **USB 数据采集项目的治理配置已完成。** 你可以继续在原来的窗口开发。第一次治理已统一模拟协议、确认每个窗口当前的位置，并保留尚未完成的曲线与导出工作。

| 窗口或来源 | 职责 | 接下来做什么 |
|---|---|---|
| 治理总控 | 项目记忆、规则同步、保存恢复与定时治理 | 跟进协议与电脑实现是否一致，把有意义的变化反馈给相关窗口。 |
| 固件与协议 | 模拟读数、帧格式与字段解释 | 保存共同输入；真实固件与设备测试另行安排。 |
| 电脑软件 | 解析、实时曲线与 CSV | 用共同输入完成界面与导出验证。 |
| 仿真验证 | 正常、断开和重连回放 | 检查数据与显示结果，给出可复现的差异。 |
| 旧硬件与接口笔记 | 参考来源 | 保留已确认约定，不作为活跃工作窗口。 |

> 各活跃窗口已分别完成原生工具连接验收并读到自己的工作入口。本地 Git 已保存选定治理文件；原业务仓库和未提交工作保留。以后可先保存进度，再对明确文件形成精确版本；保存进度不等于已交付或已被接受。
>
> 恢复演练覆盖了选定项目状态、对象、协议材料、验证脚本、Git 历史与暂存/未暂存改动。独立恢复的副本保持待机。未保存的编辑器内容和平台私有对话历史不在这份恢复集内，凭证另行管理；本例未选择网盘，因此没有声称已上传异地。
>
> 已核对官方更新来源；有新版本时先判断适用性，不自动安装。你确认的时区下，已配置一个上午报告时段和一个下午吸收进展时段，均回到原治理对话。配置已回读，首次自然触发尚待发生；我不会把本次手动执行当作定时闭环已验收。
>
> 现在建议回电脑软件窗口，用三帧输入接通曲线与 CSV。治理建立完成，工程开发继续；真实 USB 设备尚未测试。

若缺少必要窗口的连接、本地保存、定时配置或恢复验证，报告应说“配置进行中”，列出准确缺口和当前操作。不能把包已安装写成治理全部完成，也不要求你从头重装。

## 4. 正常推进后，总控怎样汇报

共同输入为：

```text
READ,42,1000,1.234
READ,43,1100,1.250
READ,44,1200,1.220
```

下面是完成相应检查后才可以给出的反馈：

> 三帧模拟数据已得到相同的序号、时间和值。解析与回放检查通过，送给曲线的输入是 1000、1100、1200 毫秒处的三个点；CSV 参考行也与它们一致。本次验证了数据链路，实际曲线界面和文件导出操作仍分别列出证据，不用解析通过代替。
>
> 断开后，解析器没有生成新测量值，并清除了未完成的半帧；重连后继续读取递增序号，旧序号没有重复写入。接下来由电脑软件窗口验证真实界面的断开提示和显示恢复。硬件接入仍是后续阶段。

随包回放程序能验证上述模拟解析、断开/重连和 CSV 数值保真；它不是完整电脑软件。若真实设备重启会把序号归零，需要另定会话或重启标记，不能直接套用“序号持续递增”的模拟假设。真实报告引用具体输入、输出和测试结果；静态曲线截图也不能代替真实界面交互。

## 5. 遇到缺口、中断或没有变化

> 电脑软件窗口的配置文件已写好，但该窗口还没有出现 TaskCarry 原生工具。请信任并重载报告列出的那个目录。我会随后核对该窗口的实际连接；已完成的协议窗口配置保留，不重装、不重新登记任务。

> 中断前，协议窗口的入口已写入，只缺回执。我核对文件效果后补齐了回执。另一个窗口的文件后来被你修改过，已保留，下一步基于新内容准备计划；其他独立工作可继续。

> 本次吸收已读的来源没有实质变化，原有进度与下一步保留，没有新建交付、安装或重开已完成任务。未能读取的来源单独列为待核对。

吸收时段无变化可安静保存，由上午报告汇总。来源未读到不是“没有变化”，也不因此编造成功或失败。

## 6. 恢复与异地并行

> 已按清单把选定协议、脚本、项目记忆与 Git 改动恢复到独立位置，并核对恢复结果。它仍属于原项目，但目前是待机副本；新位置的连接还须重新验收。
>
> 如果在另一台电脑继续电脑端开发，可使用独立工作分支，把精确版本、修改文件、验证结果和下一步交回同一个治理。若要把治理本身迁过去，先确认旧写入者停止，再核对新宿主并执行明确的移交；不能让两个副本同时改同一份治理状态。

本地独立目录恢复、上传、异地下载、真实第二台电脑接入与治理移交分别报告。没有第二台机器的实测，就不能声称异地全链路已验收；这些也都不构成真实 USB 设备验证。
