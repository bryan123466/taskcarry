# 首次安装：三步建立完整的项目治理

[已有用户更新](updating.md) · [手动后备](manual-setup.md) · [完整反馈示例](user-feedback-examples.md) · [English](../en/windows-example.md) · [繁體中文](../zh-TW/windows-example.md)

你已经在 Codex 中推进项目。TaskCarry 为已有工作增加一个独立治理窗口：记住有效决定，理解进展，把共同约定送回相关窗口，并保存可恢复的项目记忆。你仍在原来的窗口做事；是否让治理长期承担项目协调，由你选择。

下面以“USB 数据采集与曲线显示工具”为例：固件侧提供模拟读数，电脑侧解析、显示曲线并导出 CSV，仿真检查正常、断开和重连。你可以换成自己的项目，也不必为安装而新增固定数量的专业窗口。

## 1. 打开治理文件夹，发送一条提示词

建立本地 `TaskCarry` 文件夹，把[完整产品包](../../START_HERE.md#download)解压到 `toolkit/`，保留包内版本目录。在 Codex 中打开外层 **TaskCarry 文件夹**并建立独立治理对话。业务文件留在原位置；已有治理的项目使用[更新入口](updating.md)。

```text
TaskCarry/                 在 Codex 中打开的治理工作目录
  toolkit/                 解压后的产品包
  runtime/                 由助手准备的独立运行环境
  .taskcarry/              持久项目状态、对象与工作台入口
  .agents/skills/          本项目使用的治理方法
  .codex/config.toml       项目连接配置，保留其他设置
```

<a id="install"></a>

替换方括号，发送下面这条完整提示词。除此之外的配置由治理带着完成：

> 请把这个对话建立为我已有项目的 TaskCarry 治理总控，核心职责是项目记忆与治理。产品位于：[含 START_HERE.md 和 packages/ 的解压目录]。项目线索是：[已有目录、对话或简短目标；范围未定时请先帮我整理候选]。
>
> 先读产品入口、taskcarry-project-setup Skill 及其引用资料，再检查已有安装、治理、任务、目录和 Git。继承有效决定、成果、任务关系、暂停位置与未提交工作，复用已有配置，不重新初始化已有项目。
>
> 先向我说明你理解的目标、当前进展与建议接入范围。范围未明确时，只根据当前工具可见且获准的索引与目录整理候选；选定后再读取相关内容，不扫描无关历史。已确认事实与建议分开；读不到原对话时，指导原窗口给出最小交接，不假装已理解。旧资料可作为参考来源，不必把它们都变成工作窗口。
>
> 根据现有对话建议分工，保留原任务身份与职责。为每个活跃窗口落实实际工作目录、本地 Git 工作或保存位置和写入边界；复用已有仓库与核实的作者配置。把 MCP、Skills 和当前工作入口接到同一个治理，保留专业说明及其他设置，并让每个窗口分别核对自己的真实连接、原任务、进度与共同约定。我仍可直接在专业窗口推进，不要求所有行动经过总控分派。
>
> 完成本地治理版本保存，登记官方更新来源并检查一次；发现新版本先判断是否适用，不自动安装。建议每天一个上午报告时段和一至两个吸收进展时段，与我确认时间和时区后建立或复用原治理对话的原生自动化，不改变模型和权限。
>
> 做完第一次治理：梳理决定、依赖和未完成工作，核对问题、修正与实际效果，把需要更新的共同约定送到相关窗口并核对它们读到的内容。确定必要状态、对象、Git 历史与未提交改动、项目材料和能力版本的恢复范围，制作本地恢复集并独立恢复验证，恢复副本保持待机。网盘或私有远端由我选择，上传、下载与恢复分别验证。
>
> 按产品的完整治理验收清单补齐必要配置。需要我信任目录、重载、登录或决定范围时，只告诉我当前需要的操作和目标，之后继续核对。最后用自然语言给出项目理解、各窗口职责、实际完成与缺口、下一步建议；技术证据作为可查附件。区分配置完成、自然定时触发、AI 实际执行和报告送达。中断后保留原身份，先检查实际效果，只补缺少的步骤。长期项目协调是否交给总控，由我选择。

## 2. 由治理带着完成接入和第一次治理

治理先说明范围与理解，让你确认遗漏或归类错误。一个现实项目可以跨目录、仓库与历史对话；名称相似不等于同一任务。下面是本例会得到的具体安排：

| 现有工作 | 治理整理出的职责与下一步 |
|---|---|
| 固件与协议对话 | 明确 `READ,42,1000,1.234` 的字段与换行规则，保存三帧稳定模拟输入。 |
| 电脑软件对话 | 用同一输入接通解析、曲线和 CSV，逐项核对输出。 |
| 仿真验证对话 | 先验正常数据，再回放断开与重连，确认不造数据、不重复旧点。 |
| 旧硬件与接口笔记 | 作为来源继承有效约定，不算活跃窗口、不重开已完成工作。 |

这些职责可以按已有窗口合并，不要求新建三个窗口。真实设备测试单独安排，本例先用模拟数据。治理应同时完成以下工作，而不是只给你一份待办清单：

- 保留各窗口的原任务、进度、专业说明和未提交工作，明确实际目录、Git 保存位置及并发边界。没有合适工作目录的窗口，由治理指导完成实际关联或在正确位置接续；每个窗口不需要一个新 GitHub 账号。
- 准备同一治理的连接与工作入口，由每个活跃窗口实际调用原生工具并确认读到的当前约定。配置已生成、入口已发布和窗口已读到分别核对。
- 完成本地 Git 保存、官方版本检查、第一次治理、恢复覆盖说明和独立恢复演练。普通资料可留原位，但必要材料要明确纳入恢复范围，凭证另管。
- 完成一个上午报告加一至两个吸收时段的配置与回读。时间及时区由你确认，原生信任或登录等必要操作才交给你。

本地 Git、定时配置、更新检查和首次治理是标准配置。网盘与私有远端是可选保存位置，拒绝它们不会制造缺口。遇到宿主限制时，总控只指出当前需要你做的动作。详细命令放在[手动后备](manual-setup.md)。

## 3. 复核完成报告，按原习惯继续工作

不需要记住特殊的“完成口令”。总控依据实际验收给出报告。下面是假设必要配置均已通过的反馈示例，不是某次真实安装回执：

> USB 数据采集项目的治理配置已完成。原有固件与协议、电脑软件、仿真验证工作均已接入，旧硬件笔记仅作参考。共同约定是先用模拟读数打通 USB 串口数据格式、曲线与 CSV，无线和实物测试不在本次模拟验证内。
>
> 各工作窗口分别核对了真实连接与当前工作入口。本地版本保存、首次治理和独立恢复演练已通过；恢复副本保持待机。官方更新来源已检查。上午报告及下午吸收时段已配置并回读，首次自然触发尚待验收。
>
> 现在回电脑软件窗口，用三帧输入完成曲线与导出检查；仿真窗口再核对正常、断开与重连。你可以直接继续开发，我会持续吸收相关进展。治理已建立，不表示工程任务全部完成。

有缺项时，报告要写“配置进行中”，说明已完成内容、准确缺口和下一步。**配置完成**与**自然定时闭环已验证**分开：后者须等实际到点触发、原对话 AI 执行，且报告时段确实送达。手动执行不能代替。

以后可以直接说“继续原任务”“保存这个暂停点”或“这次修改影响哪些窗口”。中断时说：**“从原验收清单和原任务续办，先核对实际效果，只完成缺少的步骤。”**

已有用户更新继续使用原治理窗口，核对原任务、决定、来源和检查点，并用旧状态副本完成完整备份及独立恢复验证；具体流程与反馈见[更新已有安装](updating.md)。

<details>
<summary>验收依据与技术明细</summary>

完整配置使用 `complete_v1`：选定来源与有效决定、活跃窗口身份和原生连接、当前入口及读取证据、本地 Git、官方更新检查、第一次治理、恢复与定时配置均须满足。`complete_governance_ready` 不替代 `natural_trigger_verified` 或 `closed_loop_verified`。入口来源变动、回执未完成或配置被改动都要准确报告。

每个窗口的原 task/chat、cwd/Git、checkpoint、view 及消费证据，和恢复清单、包身份、时段回读均保留供核对。用户无需在主流程中抄写这些字段；具体调用见[治理 API](../GOVERNANCE_API.md)。

</details>
