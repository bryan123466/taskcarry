# 首次安装：三步建立项目治理

[已经使用 TaskCarry？从这里更新](updating.md) · [手动后备](manual-setup.md) · [English](../en/windows-example.md) · [繁體中文](../zh-TW/windows-example.md)

本手册面向已经使用 Codex 推进项目的用户。保留现有对话和文件，新增一个独立治理窗口，帮助长期记住决定、汇总进展并接续工作。是否长期兼任项目协调，由你选择。

## 1. 打开治理文件夹，发送一条提示词

建立本地 `TaskCarry` 文件夹，将[完整产品包](../../START_HERE.md#download)解压到其中的 `toolkit/` 子目录，保留压缩包内的版本目录。在 Codex 打开外层 **TaskCarry 文件夹**，新建治理对话。业务项目留在原位置；已经配置过的项目直接回到原治理窗口。

```text
TaskCarry/                 在 Codex 打开这个文件夹
  toolkit/                 解压后的完整产品
  runtime/                 由助手准备的运行环境
  .taskcarry/              持久治理记录
  .agents/skills/          已安装的治理方法
  .codex/config.toml       项目连接配置
```

<a id="install"></a>

填入产品位置和已知项目线索，发送以下提示词：

> 请将本窗口建立为现有工作的 TaskCarry 治理总控，承担项目记忆与治理职责。产品位置：**[解压后含 START_HERE.md 和 packages/ 的文件夹]**。项目线索：**[目录或已有对话；尚未选定时请先协助发现]**。
>
> 读取产品入口、taskcarry-project-setup Skill 及其引用。初始化前核对实际已有状态，保留我的文件、决定、未完成工作和设置，复用有效安装与身份。在本次接入范围内准备独立运行环境和项目级连接。
>
> 我已给范围时按范围接手；未给时先有限列出可读取的对话、目录及候选项目，说明分组依据和不确定性，让我选择后再读取相关历史。旧消息作为来源资料。继承已确认目标、成果、职责和接续位置，只向我补问缺失信息。
>
> 带领完成所选持续工作窗口的实际目录、本地 Git 工作或保存位置、任务绑定和 MCP 连接；仅作历史参考的对话保留来源即可。复用已有仓库和核实过的提交作者配置，处理并发写入隔离。不能代办宿主操作时，只给我当前必要的一步及准确目标，完成后核验并继续。
>
> 完成本地治理 Git 保存、官方发行来源与通道登记及一次更新检查。建立或复用绑定本原治理窗口的原生定时治理，包含官方更新评估与本地保存；时间和时区未指定时在接入中确认，保持模型和权限。发现更新不等于授权安装。私有远端和网盘由我选择是否启用。
>
> 保存可接续清单。完成后给出继承事实与未知项、各工作窗口职责表、真实连接/Git/调度/更新结果、剩余操作和下一步建议。治理与记忆是标准职责，长期项目协调可选。不要制造示例交付或重做已完成工作。

## 2. 跟随总控继承并接入现有工作

总控根据实际可读来源提出项目范围，你可以合并、拆分或排除候选。一个现实项目可以有多个目录、仓库和已有状态来源；总控明确各自路由，不因目录不同强拆项目，也不合并已有数据库。

每个持续工作窗口都要明确职责、任务、真实目录与 Git 位置。已有仓库优先复用，并行写入时准备合适的独立工作树目录。原对话没有合适目录时，完成真实关联或在正确目录建立承接窗口，继承原进度。仅写一个路径不会改变宿主工作目录，也不需要每个窗口单独注册 GitHub 账号。

总控保全其他服务和设置，准备并合并项目配置。必要的信任或重载后，各活跃窗口分别真实调用原生 doctor/status；读过历史不等于已接入，CLI 成功也不能代替另一个窗口的 MCP 验收。缺失历史才使用[后备文档](manual-setup.md#existing)中的短交接提示词。

本地 Git、原治理窗口定时任务、官方更新检查均在此步完成配置，不默认留给用户安装后补做。大型文件可保留外部位置，记录内容身份和备份覆盖。普通文件检查点用于保全与恢复，不替代专业窗口的标准配置。

## 3. 查看验收报告，继续原来的工作方式

无需特殊完成口令。配置有真实结果后，总控应给出：

- 继承的目标、有效决定、已完成成果、暂停点和待澄清事项。
- 所选工作窗口的职责、任务、真实目录、Git 关系和实际连接；仅作历史来源的对话另行标明。
- 本地治理提交、定时任务的原窗口/时间/时区及配置回读、官方更新通道与评估结果。
- 确实仍需操作的一步、可选远端/网盘覆盖，以及建议在哪个窗口推进什么工作。

第一次自然定时触发在实际发生后补验；配置回读、手动运行和自然触发分开报告。必要窗口或标准项没完成就保留具体缺步。你可以继续已有可用工作，总控不能因此声称“全部完成”。

日常直接在专业窗口说“接着上次未完成的工作”“保存这个暂停点”或“复核已接入任务的进展”。中断后说：**“请从已保存的接入清单继续，先核对实际效果，只补剩余步骤。”**

### 你应该看到的完整对话示例

以下为合成示例，展示交互方式，不代表你的宿主已经验收。

| 对话环节 | 示例内容 |
|---|---|
| 总控提出候选 | “发现一个预约系统候选，包含需求对话、界面开发和旧测试讨论，分布在两个目录；另有一个资料阅读对话可能独立。这是基于可见索引的建议。” |
| 用户选择 | “接入预约系统；旧测试讨论只作参考，资料阅读暂不接入。” |
| 总控继承 | “预约规则已有确认，界面还未完成。建议保留两个活跃窗口，不增加专业线程。这里列出决定及来源。” |
| 继续配置 | “原 Git 仓库可复用，界面窗口已有独立工作树；需求窗口还需一次信任/重载。请在这个准确目录操作，随后核对原生返回。” |
| 遇到能力缺口 | “当前接口读不到旧测试对话，只需要为它补这段交接；其他已完成结果保留。” |
| 输出验收 | “两个活跃窗口均通过自身原生验收；本地治理文件已提交并核对。每日治理绑定本原窗口和确认的时区，首次自然触发待发生。官方更新已检查，网盘选择不启用。下一步回到界面窗口接续原任务。” |
