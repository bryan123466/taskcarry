# 首次安装：三步建立完整的项目治理

[更新与接续](updating.md) · [手动后备](manual-setup.md) · [反馈示例](user-feedback-examples.md) · [无人机项目实例](../../examples/vision-drone-governance/README.md) · [English](../en/windows-example.md) · [繁體中文](../zh-TW/windows-example.md)

这份手册面向已经用 Codex 推进项目的人。建立一个独立的治理窗口，由它整理项目记忆、接入已有工作，并带你完成配置。你仍然可以直接在原来的对话中工作；是否长期让治理同时协调项目，由你选择。

## 1. 打开治理文件夹，发送一条提示词

建立本地 `TaskCarry` 文件夹，把[完整产品包](../../START_HERE.md#download)解压到 `toolkit/`，保留包内版本目录。在 Codex 中打开外层 **TaskCarry 文件夹**并建立独立对话。原有业务文件保持原位置。

（如果已安装 TaskCarry、使用其他治理工具或已有治理对话，需要更新或接续，请参阅[更新与接续入口](updating.md)。）

```text
TaskCarry/                 在 Codex 中打开的治理工作目录
  toolkit/                 解压后的产品包
```

**直接复制下面的完整提示词，无需填写产品路径：**

> 请读取当前工作目录下 toolkit 中的 TaskCarry 产品入口和接入 Skill，带我建立项目治理。先检查已有治理、安装和工作状态，保留原有规则、决定、任务及未完成工作。
>
> 先只读整理当前工具可见的对话索引，给出可能的项目及包含的对话，让我选择；选定后再读取相关历史。为我准备原窗口的完整接入提示词，并按实际需要建议新增窗口。
>
> 随后按实际工作目录复用本地 Git、MCP 和 Skills，让同目录中的原对话各自保留任务身份，不为接入要求每个对话另建目录。协助完成项目记忆、首次治理和恢复验证。与我确认时间及时区后，配置日常治理和官方更新检查。需要我操作时，一次只给当前必要的一步，写明按键或入口、准确目录、用途以及完成后回复什么。新连接尚未加载时，先备好配置和原聊天的项目关联，再带我集中重启一次 Codex，返回原聊天逐窗验收；已验收成功的连接不重复重启。中断后继续缺少的步骤。
>
> 最后告诉我已经接入哪些窗口、分别负责什么、还有哪些缺项，以及接下来建议做什么。我仍然可以直接在原来的工作窗口推进。

产品目录就是 `toolkit/` 中的 TaskCarry 套件，由助手从当前目录核对。读取套件让助手了解治理方法；**你的项目内容来自随后选定的对话和文件**。包缺失、内容不完整或存在多个无法区分的包时，助手才说明具体问题。

## 2. 由治理带着完成接入和第一次治理

接下来只需跟随治理给出的当前一步。它先告诉你这次可读取哪些对话索引、是否包含归档、是否还有下一页，以及哪些范围无法访问；再整理候选项目，供你选择。索引包含标题、目录等线索，只有在你确认项目范围后，才读取相关历史内容。你也可以直接指定项目，跳过无关候选。

选定后，治理应依次完成：

| 你会收到什么 | 治理负责完成什么 |
|---|---|
| 项目理解与接入建议 | 整理原成果、有效决定、任务和未完成位置；区分已有事实与建议。旧参考对话可以仅作资料来源。 |
| 每个窗口的具体操作 | 为原窗口给出已填好目标和内容的接入提示词；确需新增职责时，再给建立位置、完整激活提示词及预期回执。窗口数量按项目需要决定。 |
| 需要你参与的当前一步 | 准备真实工作目录、本地 Git、项目配置和 MCP。信任目录、登录或重载由宿主要求决定；治理说明去哪里操作、成功会看到什么，再继续核验。 |
| 接入和首次治理结果 | 逐窗口确认实际连接、原任务与当前入口；整理共同记忆，精确保存选定文件，检查官方更新，完成本地恢复演练。 |
| 日常节奏建议 | 与你确认时间及时区后，创建或复用返回原治理对话的报告和进度整理时段，并读回实际配置。 |

**已有对话不用重新建立，也不要求每个对话单独建目录。** 多个原对话可以共用已有业务目录及其连接配置，各自保留原任务、检查点和记忆入口。只有并行写入确实需要隔离时，治理才建议独立 Git 工作树。

若原对话的目录还没有在 Codex 中打开并信任，治理先核对并写明其准确原目录，再带你做这一小段操作：

1. 在当前 Windows Codex 中按 **Ctrl+O**；其他界面使用“打开／添加项目文件夹”入口。
2. 选择治理给出的**原工作目录**，打开这个已有目录。此时**不用新建聊天，也不用复制文件**。
3. 若出现信任提示，核对是该目录后确认。
4. 回到治理对话，回复“已打开指定目录，并确认了出现的信任提示”；没有出现提示则如实说明。治理会核对配置和原聊天的项目关联。
5. 治理确认本次各目录准备完成、需要加载新连接后，先保存正在进行的工作，**退出并重新打开 Codex 一次**。可以等本次所有目录准备好后一起重启，不必每打开一个目录就重启。
6. 回到**原治理聊天**回复“已重启”，并回到各个**原工作聊天**完成治理给出的验收提示。保留原历史、任务和文件，不重新安装或创建替代聊天。

这些操作让宿主登记并信任原目录，**将原聊天关联到该项目并加载其中的连接配置**，仍使用同一份治理记忆。治理按宿主能力完成关联，核对实际工作目录没有改变，再逐窗原生调用 `taskcarry_doctor`、`taskcarry_status`，核对版本、来源、control、原任务和最新检查点。这条 Windows Codex 接入路线在新连接、目录信任和聊天关联准备好后，明确安排一次重启，再回原聊天验收。已实际验收成功的连接跳过重启；其他宿主采用其支持的加载方式。侧栏出现聊天或重启完成本身都不代替原生验收。[查看已填目录的反馈示例](user-feedback-examples.md#open-existing-project)。

未挂在项目下的活跃对话，先核对它实际使用的目录与工具，优先保留原对话并按宿主能力关联该目录。这个标签本身不表示不能使用 MCP，发送提示词也不会改变窗口目录。仅作历史参考的对话可只登记为来源，无需给原窗口配置 MCP 或 Git。若宿主无法读取所需历史或完成连接、调度，治理只给当前缺步及续办方法，必要时链接[手动后备](manual-setup.md)。

本地版本保存、工作窗口连接、恢复验证、日常治理配置和官方更新检查属于标准建制。私有 Git 远端和网盘可以随后按你的选择配置；未选择它们不影响本地治理。发现新版后先判断是否适用，不会因此自动更换运行包。

发现适用的官方 Core 更新时，治理先准备保全、配置和重启方案，再询问是否维护；未变或已暂缓的候选不重复追问。见[官方更新与维护闭环](core-update-maintenance.md)。

## 3. 复核完成报告，按原习惯继续工作

治理应给你一份容易理解的报告：

- **理解了什么：** 项目目标、继承的决定和成果、仍需确认的内容。
- **接入了哪些窗口：** 每个窗口的职责、原任务、实际工作位置及连接结果。
- **完成了哪些配置：** 本地保存、项目记忆、恢复验证、官方更新检查和日常时段的实际结果。
- **还缺什么：** 具体缺步、影响范围和当前必要操作。未完成项不会被写成“已完成”。
- **下一步怎么做：** 回到哪些原窗口继续什么工作；哪些建议由你决定。

“配置已完成”与“自然定时闭环已验证”分开报告。时段配置读回后，仍要等它真正到点，再核对原治理 AI 是否执行、是否完成保存和是否送达报告。某一步等待宿主操作，不应抹掉其他已经完成的结果。

之后你可以在原专业窗口说“继续上次未完成的任务”，或在治理窗口说“检查当前项目进度”。中断时说“保留已完成的结果，继续剩余配置”，不必从第一步重来。
