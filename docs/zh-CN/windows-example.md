## 1. 建立治理总控窗口

如果这个项目已有有效的 TaskCarry 治理总控，回到该窗口，让它核对并继续原接入即可。否则，在 Codex **新建一个独立窗口**，例如命名为“项目治理总控”。原主对话和专业对话继续保留工作与历史。

为治理选择独立目录。首次安装的合成示例为 `C:/TaskCarry/control`，将选定产品 ZIP 解压到 `C:/TaskCarry/toolkit`。RC6 压缩包自带版本目录，因此包含 `START_HERE.md`、`packages/`、`docs/` 和 `skills/` 的实际产品根为 `C:/TaskCarry/toolkit/taskcarry-0.2.0rc6`，下方提示词填写这个实际产品根。新治理窗口打开 `control`。原业务文件留在原位置。宿主权限允许时可让助手准备目录；需要时查看[手动准备](manual-setup.md#install)。无关项目使用另一个根目录，已有绑定的 control 不直接搬动。

准备一个项目定位线索即可：项目目录、相关旧对话的名称或链接，或者两者都有。项目中尚无名称和简介时再补充；不用先决定任务 ID、分支名或专业窗口数量。

<a id="install"></a>

### 发送一条接入提示词

替换两处填写项，将下面整段发给治理窗口。安装与承担治理职责在同一次对话中完成。

> 请将本窗口建立为这个现有项目的 TaskCarry 治理总控，负责治理与项目记忆。
>
> 项目定位线索：**【项目位置和／或相关已有对话】**。产品解压目录：**【包含 START_HERE.md 和 packages 的目录】**。
>
> 请读取该产品包的 START_HERE.md、taskcarry-project-setup Skill 及其 references/onboarding.md，核对实际宿主能力、已有安装和治理登记。如已有有效 TaskCarry 总控/control，直接复用；保留原工作对话、任务身份、文件与未完成位置。
>
> 定向读取获准资料，恢复项目目标、已完成成果、有效决定、原分工和接续点。将确认事实、你的建议和证据缺口分开。通过对话完成获准安装与工作窗口接入，维护可接续的清单；无法代办宿主操作时，只给我当前必要的一步，填好目标位置和内容。
>
> 接入时给我一次项目梳理、分工和下一步建议，新增专业窗口可以为零。说明我可以选择让你长期兼任项目协调；保留我直接在各工作窗口推进的方式，不把这次建议视为持续派工或定时调度授权。
>
> 最后完成一次有限复核，说明继承了什么、实际安装和连接情况、剩余缺步、各窗口如何读取与保存相关进展，以及我的下一步。不要为了接入制造样例交付，也不要重做已完成成果。

**已经进行到一半时：**直接说“请从保存的清单继续接入”。治理核对实际结果后补齐缺步；待重载不需要再粘贴角色提示词或重装。

## 2. 由治理带着接入已有工作

治理先核对已有情况，再带领完成剩余配置。治理目录为空，不代表业务项目是新项目。确实没有旧成果的新项目，也可以在同一对话中梳理目标，并在核对后建立起始基线。

<a id="existing"></a>

### 保留原窗口、成果和决定

第一份接手摘要应列出已有成果、有来源的有效决定、任务与责任人、暂停事项和下一步。已接收成果保持历史事实；新的理解建议先作为候选，确认相关修订后才成为有效稿，不悄悄覆盖原决定。

治理只使用实际可访问且与项目相关的上下文。不能直接读取某个旧窗口时，它会准备一段最小交接提示词；[手动后备](manual-setup.md#existing)保留了拆开的转交步骤。它不会扫描全部私人聊天，也不承诺持续监控所有窗口。

分工根据实际需要提出。一个原工作窗口加治理窗口就可能足够。只有独立成果、并行价值、文件归属与依赖确有需要时再增加专业窗口。多个旧窗口共用目录时，先核对活跃写入者并保全现有工作，再调整归属或分离工作区；改个聊天名字不会隔离文件写入。

<a id="mcp"></a>

### 完成实际工具连接

同一项目的各工作台使用同一个 control。治理为各工作台生成正确运行时、已登记任务和工作区对应的接入材料及四项 Skills；材料可以放在工作台目录，MCP 仍绑定原 control，不在每个工作区再初始化一个数据库。

助手把生成服务合并到目标目录的 `.codex/config.toml`，例如治理使用 `C:/TaskCarry/control/.codex/config.toml`，并保留原设置。让目标 Codex 聊天打开或选用同一目录，完成必要的项目信任，再使用宿主支持的操作重启/重载 MCP。另一目录的配置不会让当前聊天自动连接。宿主动作需要你操作时，助手给出当前一步，收到回复后继续。[手动配置与验收](manual-setup.md#mcp)提供准确落点、官方依据及后备步骤；setup 本身不激活宿主。

连接结果分为三项：**材料已生成、宿主已加载、该窗口原生 doctor/status 调用成功**。隔离 CLI 成功可作为后备证据，不能代替原生 MCP 成功。治理记录实际版本、解释器、模块及 control/任务绑定；一个窗口成功不表示另一个窗口也已加载。

## 3. 按原来的习惯继续推进

你可以直接在原有或协商新增的专业窗口工作。在有意义的暂停、成果或决定变化处，由助手保存相关进展与下一步；接续前读取当前任务和关联的有效决定。治理汇总已接入的证据并核对缺口。共享进度不会自动合并所有工作区的代码。

可以说“继续上次未完成的工作”“保存当前暂停位置”或“整理已接入任务的当前进度”。稳定 Git 阶段可单独交付，未完成工作继续保留。普通文档 checkpoint 无需 Git，保存的是选定文件；完整的非 Git 成果交付与接收合同仍是后续能力。

| 工作方式 | 治理负责什么 | 你怎样工作 |
|---|---|---|
| 治理与记忆，默认 | 来源、有效决定、任务进展、接续与有计划的成果接收 | 直接在工作窗口推进，按需找治理。 |
| 兼任项目协调，可选 | 上述记忆，加优先级、依赖与分工建议 | 可以在总控讨论整体安排，也继续在其他窗口工作。 |

这项偏好可以调整，不需要重建项目。首次项目梳理不会自动开启持续协调或定时任务。

<a id="check"></a>

### 接入完成时应该看到什么

- 继承的目标、决定、任务、已有成果和未完成位置清楚，建议与未知仍有标识。
- 唯一 control 及需要时的接收基线明确，原工作与用户配置得到保全。
- 实际安装、每个宿主连接和剩余动作分别有证据。
- 各工作窗口知道怎样读相关上下文、保存进展与接续；新增专业窗口可以为零。
- 首次有限复核报告实际结果或就绪状态。checkpoint 不等于交付，接收不等于业务验收，计划不等于已经执行。

### 按需增加的能力

定时治理是可选项。需要时，治理复用首次复核结果，通过宿主实际调度能力配置；保存提示词不等于已验证自然触发。详见[定时治理](automation.md)。

<a id="private-git"></a>

[私有 Git 与备份](remote-and-multicomputer.md#private-git)只覆盖实际纳入并核实的内容。记录路径不等于备份，普通 Git 推送不会自动保存在线 control 数据库或全部未提交工作。

<a id="multi-computer"></a>

[多电脑协作](remote-and-multicomputer.md#multi-computer)需单独验证。本版不提供自动主节点选举或共享数据库多方写入，接通 MCP 也不代表所有平台和多机流程已经完成。

日常选择见[操作索引](operation-manual.md)；遇到具体缺步时，查看[手动后备](manual-setup.md)和 [CLI/MCP 参考](../COMMANDS.md)。
