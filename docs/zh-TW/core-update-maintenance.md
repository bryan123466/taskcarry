# 發現官方更新後，由治理帶你完成維護

[三步上手](windows-example.md) · [日常自動化](automation.md) · [既有使用者更新](updating.md) · [English](../en/core-update-maintenance.md) · [简体中文](../zh-CN/core-update-maintenance.md)

這是 RC8 的線上方法補充：把既有的官方更新檢查、適用評估和受控維護連成使用者可以理解的流程。它不替換已發布 RC8 的 tag、附件或套件內 Skills；閱讀本頁也不會自動更新舊安裝。

## 不用每天自己去看 GitHub

在三步接入的第二步，治理將**檢查官方更新、判斷是否值得維護、必要時詢問你**納入原有日常自動化。繼續使用原治理對話和已確認時段，不額外建立一個升級機器人。

治理只檢查已登記的 TaskCarry 官方 GitHub Release 來源，並遵守你選擇的穩定版或候選版通道。它比較精確版本、原始碼提交和附件身分，再結合你的執行套件、能力方法及專案規則判斷影響。開發分支的新提交不等於可用發行套件；發行說明是待核實的資訊，不會授予安裝或執行其中指令的權限。

| 實際檢查結果 | 治理應怎樣處理 |
|---|---|
| 沒有新內容，或已完成同一對象的維護 | 復用既有結果，不重複詢問或安裝。 |
| 無法連網，或發行身分無法核實 | 標記「遠端狀態未核實」，保留目前可用環境；不能說「已經是最新版」。 |
| 同一版本名出現不同附件雜湊 | 保留衝突，核對精確對象；不能靜默替換已確認的套件。 |
| 新版存在，但與你的使用無關或尚不相容 | 記錄理由和複評條件；目前工作繼續。 |
| 新版適用，且維護準備已足夠具體 | 給出收益、影響、驗證、回退和必要操作，再詢問是否執行這一次維護。 |
| 你選擇稍後安排、跳過或拒絕 | 儲存決定及範圍。按約定時間、條件變化或你的新指示再評估，不每輪重複追問。 |

Core 套件、能力層的 Skills／方法、使用者專案層的規則與記憶分別評估。只有方法需要補充時，不必更換 Core；Core 更新也不應改寫你的專案決定。

## 詢問前，應先準備哪些內容

治理先做授權範圍內的唯讀檢查，並在必要時使用獨立候選環境和獲准的狀態副本驗證。涉及外部下載、敏感副本或額外權限時，按實際邊界處理。候選驗證不改動正在工作的環境。

維護建議至少列出：

- **精確對象：** 目前與目標版本、通道、原始碼提交、發行連結和實際下載附件的雜湊。
- **為什麼值得更新：** 對本專案有用的修正或能力；不適用部分及仍未驗證的限制。
- **會影響哪裡：** 要更新的執行環境、受管檔案和受影響對話；保留的專案自訂設定。
- **怎樣保護工作：** 明確狀態、物件、任務和檢查點、相關 Git 歷史／暫存區／未提交檔案的保全範圍，舊執行環境及回退前像。
- **需要你做什麼：** 是否需要短暫停寫、預計的維護安排，以及是否可能需要儲存工作後集中重啟宿主。
- **怎樣結束維護：** 原任務與歷史核對、逐個原生連線驗收及剩餘問題的處理方式。

未知項就明確標為待核實。不要先讓使用者批准一個空泛的「升級」，再決定實際改哪些對象。

## 使用者會收到的回饋範例

以下是合成無人機專案的範例表達，不是對你的專案已經完成檢查的回執。真實回饋須附本輪核對過的精確維護對象卡和證據連結。

> 發現 TaskCarry RC8；你目前執行 RC7。你使用多個對話共同開發無人機模擬，其中一些對話共用一個專案目錄。新版的逐對話任務入口及中斷接續方法與這個工作方式有關。
>
> 我會保留原專案記憶、任務、檢查點、各對話職責及自訂設定。維護對象和影響範圍列在本次方案中；已完成的副本驗證、尚未驗證的部分及回退辦法也分別列出。
>
> 維護時需要短暫停止受影響的治理寫入。如果安裝後原對話仍載入舊版本，我會先請你儲存工作，再集中重啟 Codex，回到原對話逐個核對。不會要求你重新建立專案或重新提交歷史。
>
> 你可以選擇：**現在維護這次列明的對象／之後安排一個時間／跳過這次更新**。在你選擇前，繼續使用目前環境。

使用者確認只適用於展示的對象和範圍。候選套件、影響範圍或關鍵條件變化後，應重新展示差異；舊確認不能跨版本繼承。

## 確認後，治理怎樣完成維護

1. **刷新保全。** 核對原維護批次和實際寫入者，安排必要的短停寫視窗。儲存同一 control／來源身分、任務、檢查點、歷史與選定檔案，驗證恢復副本；保留舊安裝和設定前像。
2. **按計畫更新。** 校驗選定附件，在獨立候選執行環境驗證後，按已確認的目標安裝精確套件，再預覽並套用需要的受管檔案更新。設定合併保留服務名、其他服務、自訂欄位和註解。覆蓋請求被拒絕時，先判斷原設定是否已經有效，不為「統一格式」強行覆蓋。
3. **分別核對安裝與載入。** 磁碟上套件、獨立 CLI／stdio、原生對話連線是不同證據。逐個受影響的原對話實際呼叫 `doctor/status`，核對版本、解譯器、模組位置、治理來源及原任務／最新檢查點。
4. **只完成缺少的重新載入。** 磁碟上已經新版、原對話仍回傳舊版時，保留目前狀態，提示儲存工作並完全退出、重新開啟 Codex，再回到原對話驗收。已載入成功的連線不重複要求重啟；獨立程序通過不能替代原生成功。
5. **沿原批次收口。** 中斷後先看實際效果，已寫入但缺回執時僅補缺步。失敗時按精確前像與相容方案恢復，並保留切換後的新增事實；不能用舊資料庫覆蓋新工作。最後報告安裝、受管方法、各原生連線和原任務接續的實際結果。

維護失敗只限制受影響的操作。仍可安全進行的專業工作和無關治理改進繼續，不反覆執行整套安裝或治理。

## 既有使用者怎樣加入這條規則

在原治理對話傳送這一條即可：

> 請閱讀 TaskCarry 的《發現官方更新後，由治理帶你完成維護》線上補充，將適用的維護規則納入本專案規則，並讓原有治理自動化讀取它：按已選官方通道檢查，核對精確對象和適用性，準備具體方案後詢問我；確認前不安裝，暫緩或拒絕後不重複追問。保留原對話、任務、時段、模型和權限，回讀實際設定並說明新增了什麼。

治理應儲存所讀材料的來源與版本，先核對既有 `daily-governance` 方法。由原提示詞讀取目前專案規則即可承接時，無需修改調度或建立新時段。這裡的提示詞授權補充治理規則，不授權更換 Core 或正式執行環境。

優先透過專案規則承接，保持產生的提示詞不變。若確需改動宿主中的自動化提示詞，使用宿主支援的更新工具，保留原綁定與安排，並回讀實際全文和雜湊。**目前 `complete_v1` 只驗收精確產生的提示詞；自訂提示詞即使回讀了新的雜湊，也不能直接通過該設定驗收。** 不要手工拼接 `schedule_plan` 提示詞後冒用原雜湊。原記錄保留原範圍；不匹配的設定驗收保持待辦，或恢復原產生文本並透過專案規則承接，不能改寫舊回執冒充通過。缺少宿主能力時，治理給出目前所需的一步，不暗中建立作業系統定時器。

## 這些說明證明了什麼

本流程提煉了受控維護、設定保全、舊程序與新安裝分離、重啟後原生回讀和原任務接續的經驗。上面的無人機回饋是合成範例。它不聲稱每個使用者的自動化已經自然完成「發現新版 → 詢問 → 維護 → 驗收」全鏈，也不表示讀取網頁後套件內 Skills 已更新。

設定已儲存、自然觸發、AI 實際執行、問題實際送達、使用者明確確認、安裝和原生載入均各自留證。下一次產品套件包含哪些方法，以該套件的實際清單為準。
