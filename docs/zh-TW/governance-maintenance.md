# 工作持續推進時，如何維護治理工具

[English](../en/governance-maintenance.md) · [简体中文](../zh-CN/governance-maintenance.md)

TaskCarry 將專案記錄保存在 control 目錄，由已安裝的工具處理這些記錄。更新工具的目的，是讓下一輪接續原有工作；不需要重建專案、重新提交歷史成果，也不需要為了更新一個 Skill 而合併業務分支。

本頁是供治理助手按需查閱的技術參考。既有使用者從[更新提示詞](updating.md)開始，由助手處理這裡的細節。標準排程見[定時治理](automation.md)。

## 三種更新，各自解決一件事

| 更新內容 | 使用方式 |
|---|---|
| 工具與專案 Skills | 評估精確候選；在授權內準備獨立執行環境，預覽受管檔案/設定修改，保留舊環境並核驗原生宿主載入。 |
| 共用專案進度與規則 | 讀取目前 Core context/facts，只向受影響工作台發布帶來源版本的 view 並核對消費；不因此合併業務 Git 分支。 |
| 專業任務需要的已接收程式碼或成果 | 使用明確的 `adopt` 計畫；這是業務更新，繼續核對衝突並保全未完成工作。 |

## 每輪先看目前需要處理的工作

`agenda` 提供現有 AI 一份有限清單，包括未完成操作、已提交階段與需要決定的材料。暫停、等待的任務持續保留，不會因此增加交付義務。已完成歷史仍可從完整狀態與記錄查詢。

```json
{"limit": 20}
```

透過 `taskcarry_agenda` 傳送此請求，也可將其儲存為 JSON 請求檔案，使用 CLI 的 `agenda` 動作。返回 `next_cursor` 時可繼續翻頁；游標綁定同一份目前輸入，工作變更後應重新選取。比較兩次觀察時，將先前的 `fingerprint` 作為 `previous_fingerprint`。`changed: false` 不會關閉未完成事項，也不授權再次嘗試。

清單不會執行修復、啟動另一個 AI 或建立定時任務。符合條件的經驗是建議，執行者仍須核對實際效果。已建立索引的狀態庫只選取目前記錄和必要前序，不載入無關的已完成歷史。筆數上限限制返回內容，不代表全部目前輸入處理、資料庫查詢或 AI 對話具有相同的耗時上限。

## 維護目前事項索引

新專案會自動建立衍生索引。舊索引或失效索引不會改變原始記錄：`agenda` 回退為完整選取，並報告 `storage.upgrade_required`。安裝選定工具版本、確認相關治理寫入者已安全停止後，對既有 control 執行明確的 `upgrade` 動作：

```sh
python -I -X utf8 -m taskcarry --project ./control upgrade
```

使用實際既有的 control 路徑，不重新初始化替代專案。這個動作在同一個交易內只重建衍生索引，可安全重複執行，原記錄和事件保持不變。之後核對 `storage.mode` 為 `indexed_current_v1`、`storage.upgrade_required` 為 false。這不是套件升級器，也不遷移業務檔案。舊版用戶端再次寫入可能使索引重新失效，應先停止使用該舊寫入者，再重建。

## 保留核對依據與本輪精確範圍

已授權的宿主工具提供相關證據後，`observe` 儲存來源引用、已核對版本、登記的任務與工作區，以及明確的階段或材料關聯。相同觀察直接重用；變化時需帶上前一版本，避免舊資訊覆蓋較新依據。記錄不會抓取對話、證明來源真實或授予存取權限。保留來源引用，不複製敏感對話正文。

本輪有明確選取的工作時，`run` 以具名階段、操作和相關觀察建立記錄。結束時核對這一範圍內已記錄的終態，列出未完成物件和發生變化的觀察，不重放操作，也不把後來新增的工作悄悄加入原範圍。先透過相應操作工具核對實際效果；本輪結果彙總這些記錄，不是獨立的 Git 稽核。新增工作與專案總體狀態仍需和本輪範圍分開說明。

這些變化的設計依據與定向合成檢查見[治理演進報告](governance-evolution.md)。

## 安裝中斷後接續完成

升級前先核對目前接收範圍與未完採用。`reconcile` 計畫支援 `limit`，預設 20、最大 100，先選未完接收操作，再選新交付，其身分也進入凍結計畫。計畫完成只涵蓋所選範圍；後來新增的交付仍待處理並個別報告。agenda 的一頁不代表執行範圍。

採用準備失敗會保留具體錯誤與檢查點，讓下一輪從 agenda 找到。解決衝突後，成功後繼可明確取代它，原失敗繼續保留。不要刪除記錄或在輸入未變時重複失敗呼叫。`refresh_plan` 對已證明沒有套用效果的操作提供計畫建議，不執行替代計畫；`verify_and_finalize` 讓接收執行者核驗既有效果並補齊回執。

Setup 在修改受管理檔案前先儲存精確安裝意圖。若中斷發生在「檔案已寫好，結果尚未登記」之間，再次執行同一安裝可辨識已發生的效果並補齊記錄；已符合目標的檔案不必重複重寫。

如果你獨立編輯了受管理檔案，或安裝未完成就換成另一個候選，工具會保留現場並說明衝突。保留接續記錄，使用原候選診斷或續辦，不要透過刪除中繼資料來恢復。未受管理的檔案，即使恰好與安裝包相同，也不會因此被接管。

Setup 更新受管理檔案時，請勿同時在其他應用程式中編輯這些檔案。安裝鎖協調的是安裝操作，並不能鎖住所有外部編輯器。

## 確認實際使用哪個版本

變更執行套件前保留精確 wheel、受管檔案清單與已啟用設定。向前相容不保證可原地降級；恢復前複核整套內容及後續使用者修改。保留舊檢查點與未完操作，使用相容套件續辦。本產品沒有自動回退指令。

歷史來源快照說明當時使用了什麼，目前執行觀察或採用回執說明現在使用了什麼。軟體更新時保留兩者，不重寫歷史證據。本版不提供任意舊系統編號匯入或全部原生對話探索能力。

`doctor.runtime` 回報回答此次請求的進程實際匯入的套件版本、解譯器、模組位置，以及專案接入檔案的資訊。CLI 檢查成功不能證明先前開啟的 MCP 進程已重新載入。明確更新設定或重新啟動連線後，還應透過該連線再次核對。

原始碼指紋描述目前磁碟檔案，不能證明長駐進程已替換先前匯入的程式碼。更換執行套件後需重新啟動相關 MCP 連線；`loaded_code_verified` 保持 false，不宣稱已驗證進程記憶體中的程式碼。

TaskCarry 管理自身開發時，治理應從原始碼工作區之外的固定 wheel 環境執行，下一版本在獨立範圍開發與驗證。相關操作安全結束後再採用新版。Control 目錄持續保留：任務、檢查點與原回執屬於專案，不屬於某個工具建置。本版沒有提供通用的全自動套件升級器或跨狀態格式回退引擎。

## 一個治理對話，分別管理兩個儲存庫範圍

一個 control 仍只綁定一條接收基線。包含兩個獨立儲存庫的產品，可使用兩份 control，由一個治理對話維護共同專案總覽。Setup 時為兩個 MCP 連線明確設定不同的 `server_name`，例如 `product_core` 與 `product_app`；之後的 setup 會保留已選名稱。

```json
{"mode": "preview", "server_name": "product_core"}
```

核對預覽後，使用相同名稱執行 `mode: install`。產生的片段仍需要在宿主中明確設定，不會自動生效。兩份 control 不要同時寫入相同接收工作區；此安排沒有提供跨儲存庫統一交易或跨電腦鎖。

本地治理與使用者回饋指向相同問題時，沿用一份產品修正記錄。共用實作修正、驗證後，再登記各安裝環境是否採用。記錄修正方法與實際安裝修正，是此項工作的不同步驟。


## 完整治理與原任務接續

`complete_v1` 清單包括持久專案/副本身分、選定來源的理解、實際任務/工作區/Git 綁定、每個視窗原生連線及準確工作台消費、本機治理 Git、首次有界整輪、獨立恢復演練、官方更新檢查，以及每天兩個或三個原視窗時段。這些是標準建制內容；私有遠端、網路硬碟和長期專案協調仍由使用者選擇。歷史參考對話保留來源證據，不虛構活躍工作區。

用 `context` 讀取原任務和目前 checkpoint，用 `facts` 保留帶來源身分的決定與關係，將證據和 AI 判斷分開。`cycle` 保留準確擁有者/資源、計畫效果、實際回執、來源階段、健康和下一步。`source_scan` 只分頁列舉授權本機中繼資料；正文由宿主另行讀取。精確參數集中在[治理 API](../GOVERNANCE_API.md)。

`workbench` 凍結帶來源版本的 view，產生準確私有入口計畫後發布，保留 Git HEAD/index 和無關 WIP。核對目前指標、原任務/視窗與來源是否變化；發布、複核過的消費證據、原生 doctor/status 分別成立。來源已經變化的舊 view 不能當目前事實。

`recovery` 按選定範圍擷取一致專案集、驗證位元組並在獨立目錄恢復為 standby。恢復回執列出 `disabled_host_files`：原宿主設定保留為證據，暫不作為恢復目標的活動設定，按新機器重新產生後再用。原專案身分加新副本身分不授權雙寫入；明確移交和真實原生驗收後才啟用。[恢復參考](remote-and-multicomputer.md)區分本機擷取、傳輸與真實第二宿主證據。

舊記錄保持可讀。`identity plan/execute` 顯式採用可遷移專案身分並保留舊來源別名，不暗中合併另一專案；`upgrade` 單獨維護衍生索引。舊驗收保留原 profile，新完整建制複核復用適用證據、補真實缺口，不改寫舊歷史。

## 變更前先識別、評估與保全

初始化前對選定位置呼叫 `identify`。未知、損壞或不支援的狀態保留原狀；非空 SQLite WAL 會報告 busy，避免忽略待處理資料。等待原寫入者關閉後再檢查，不刪除其日誌。相容狀態重用。

`update_source` 登記官方通道與目前身分，`update_check` 有界唯讀查詢，`update_assess` 明確儲存適用性判斷。發現、評估、準備、安裝、setup 與原生載入分別記錄。`governance` 區分執行套件/方法與選定專案自訂規則指紋；修正已記下不代表已採用。

支援的專案層級 MCP 合併用 `connect` 計畫/執行，選定 Git 檔案儲存用 `preserve` 計畫/執行。保全註解、其他服務、使用者 AGENTS 與暫存/工作區狀態。儲存庫準備與作者核實仍是實際接入步驟；版本儲存排除活躍資料庫、執行環境、下載套件、金鑰與無關檔案。

用選定 `recovery` 恢復集涵蓋一致狀態、參照物件、Git 歷史/index/WIP 和明確素材；檢查點 `restore` 用於更窄的選定檔案範圍。擷取、本機核驗、上傳、重新下載、獨立恢復和宿主啟用分別報告。artifact 參照不是資料庫快照，也不證明遠端儲存完成。

舊欄位 `storage.upgrade_required` 只描述目前工作索引。還需核對 `storage.context_ready` 與 `storage.context_upgrade_required`：舊安裝可能已有可用 agenda 索引，但仍需明確建立 context 索引。
