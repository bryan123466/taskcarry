# 使用者回饋範例：從零散對話到共同專案記憶

[三步操作手冊](windows-example.md) · [無人機治理實例](../../examples/vision-drone-governance/README.md) · [三層架構](architecture.md) · [English](../en/user-feedback-examples.md) · [简体中文](../zh-CN/user-feedback-examples.md)

下面用「圖像辨識避障無人機」說明各階段應收到什麼回饋。你之前已經分別討論軟體、演算法和硬體，接入後希望這些工作依據相同決定繼續推進，並按需要增加產品與推廣職責。

**以下是合成情境中的回饋示意，不是安裝成功回執。** 真實回答必須引用當次讀取、設定和驗證結果，不能複製範例就宣稱通過。[獨立實例](../../examples/vision-drone-governance/README.md)提供專案資料、完整過程及驗證範圍；無人機實物、飛控、飛行安全和市場效果沒有因治理建制而得到驗證。

## 1. 先看到候選專案，再選擇讀取範圍

> 我已讀取目前宿主可存取的對話索引。活躍及封存索引分別列出涵蓋情況；仍有下一頁或存取失敗的部分會保留。這裡的「已盤點」只涵蓋列出的來源，不包括其他帳號、裝置或不可見對話。
>
> 按標題及目錄線索，我建議先確認：
>
> 1. **圖像辨識避障無人機**：包含既有軟體、演算法和硬體對話，是否屬於同一專案還請你確認。
> 2. **自訂範圍**：你也可以選擇其中幾段對話，或補充遺漏的專案。
>
> 目前只是候選分組，還未讀取這些對話的正文。請告訴我要接入哪個專案。

如果使用者已明確提供專案範圍，治理可直接確認該範圍，不必重複盤點無關對話。標題不足以判斷的內容標為待確認，不能把名稱相近當成業務關係已建立。

## 2. 選擇後，收到有來源的專案理解

> 你選擇了無人機專案。我已按確認範圍讀取相關歷史，並將結論關聯到原對話與資料。
>
> 目前目標是先形成圖像辨識避障方案及可重現的展示資料。軟體、演算法和硬體既有成果繼續使用；尚未明確的參數保留待確認，不寫成既定規格。
>
> 建議繼續保留三個原工作視窗。等方案邊界清楚後，可增加一個產品與推廣視窗，整理目標使用者、展示腳本及對外表述。它是職責建議，可以由既有視窗兼任，不要求你一定新增第四個視窗。

真實專案的目標和決定應來自讀取內容或使用者確認。這段描述僅展示表達方式。若歷史只讀到一部分，治理應同時說明實際頁數、範圍及尚未讀取的內容。

## 3. 接入提示詞已經填好，使用者只需在指定位置傳送

治理提供的是面向每個視窗的**接入卡片**，包含原對話、真實工作目錄、任務職責、同一治理來源、完整提示詞及預期回饋。它應填好自己已核實的資訊，不讓使用者手抄任務 ID、解譯器或設定片段。

下面是原演算法視窗會收到的提示詞語氣示意；真實交付還需附帶該視窗的實際接入位置：

> 繼續本視窗原來的無人機視覺演算法任務。讀取治理為本視窗發布的目前入口，核對原任務、最近檢查點、工作目錄及原生 TaskCarry 連線。保留原演算法方案、未完成比較及本機改動。
>
> 本階段與軟體、硬體共用已確認的輸入及驗收邊界。請回報你實際讀到的決定、仍缺的輸入及下一步；若入口或連線未載入，說明具體缺項並繼續不受影響的工作。

未掛在專案下的活躍對話先核對真實工作目錄與工具，優先保留原對話和歷史，並依宿主能力關聯同一目錄。不能僅憑這個標籤判斷 MCP 不可用。若仍缺信任或載入，治理只給目前必要操作，隨後回到原視窗驗收；傳送提示詞不改變目錄，也不能代替真實 MCP 呼叫。

### 多個原對話共用一個目錄時

以下仍是**預期回饋範例，不是現場驗收結果**。假設核對後發現三個原對話都在同一個既有業務目錄，以下以 `drone/` 表示：

| 原對話 | 保留的原任務 | 實際工作目錄 | 接入安排 |
|---|---|---|---|
| 無人機軟體 | `drone-software` | 既有 `drone/` 目錄 | 使用該目錄的共用連線，讀取自己的軟體任務入口。 |
| 視覺演算法 | `drone-vision` | 同一目錄 | 復用相同 MCP 與 Skills，讀取自己的演算法任務入口。 |
| 硬體方案 | `drone-hardware` | 同一目錄 | 復用相同 MCP 與 Skills，讀取自己的硬體任務入口。 |

> 三個原對話都保留，我會依這個既有目錄準備一套連線資料。你不需要為了接入分別建立三個目錄或三個新對話。各視窗繼續自己的原任務，原生連線及共同記憶的實際讀取仍逐個核對。
>
> 另一個只討論過早期選型的舊對話可以僅作歷史來源，保留引用，無需為它安裝 MCP 或建立 Git。若三個活躍視窗之後會同時修改衝突的檔案或 Git 狀態，再討論是否需要獨立工作樹。

共享設定不代表共享任務身分。治理把每個真實對話與原任務對應，未知對話先核對綁定，不會預設採用目錄中的第一個任務。

## 4. 共同決定改變時，各職責收到各自需要的變化

假設使用者隨後確認：「首個里程碑只做離線圖像回放與模擬避障決策，暫不進入實機飛行。」

| 原工作職責 | 治理整理出的影響 | 該視窗繼續做什麼 |
|---|---|---|
| 軟體 | 首階段輸入改為回放資料；不聲稱已經連通飛控。 | 整理圖像輸入、辨識結果及避障決策展示的介面。 |
| 演算法 | 根據同一組回放樣例比較辨識與決策結果。 | 保留演算法比較和失敗樣例，列明模擬的局限。 |
| 硬體 | 提供方案約束與待驗證條件；暫不開展飛行整合。 | 整理相機、運算及連線需求和尚未選定的項目。 |
| 產品與推廣 | 展示說法限定為方案及模擬能力。 | 準備產品說明和展示腳本，不把模擬寫成實飛驗證。 |

> 我已記錄你確認的新里程碑及其替代的舊範圍，保留原討論作為來源。接下來的工作台入口分別呈現每個職責需要知道的變化；入口已發布與各原視窗已讀取會分別記錄。
>
> 你仍可直接在原視窗推進，不必把每個動作都交給治理批准。涉及共同邊界的新決定會繼續彙入專案記憶。

## 5. 最後收到可核驗的完成報告

報告應使用當次真實結果，常見表達如下：

> **專案理解**：已整理目標、有效決定、各項成果及未完成位置；未確認的條件單獨列出。
>
> **工作視窗**：逐個列出原視窗、職責、任務、實際目錄與連線結果。只有拿到該視窗的原生回執，才寫「已接通」。
>
> **儲存與恢復**：說明本機 Git 實際儲存了哪些檔案，恢復演練涵蓋哪些狀態、產物及歷史；只登記位置的資料另列。
>
> **日常治理**：列出你確認的報告及進度整理時段、時區和實際設定讀回。官方更新已檢查時寫明結果與適用判斷；離線時明確仍未核實遠端。
>
> **待辦**：比如某視窗尚需重載，只給該視窗的重載和讀回步驟。標準項目未齊，不寫「全部設定完成」。
>
> **自然觸發**：尚未到點時寫「設定已讀回，首次自然執行待驗證」；真正觸發後再補原 AI 執行、儲存及報告送達證據。
>
> **下一步**：軟體完善回放介面，演算法整理比較，硬體明確約束，產品與推廣準備與證據一致的介紹。你可以直接回相應視窗繼續。

這份報告不會因為新建了幾個檔案就宣布整套治理已完成，也不會因為首次自然觸發仍在等待而要求重複安裝。

## 6. 接續與更新時，使用者仍只需說目前目標

- **中斷後：**「繼續剩餘設定。」治理先查既有計畫及實際效果，只補缺步。
- **儲存工作：**「先儲存這裡，下次繼續。」原任務保留檢查點、成果位置與下一步。
- **發現新版：**「判斷這次更新對我的專案是否有用。」治理比較 Core、能力方法及專案規則，提供適用建議與必要操作。
- **來自其他治理工具：**「接續這些規則與決定。」治理先識別來源和範圍，保留原系統，不把繼承內容冒稱為升級了第三方工具。
