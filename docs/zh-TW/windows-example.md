# 首次安裝：三步建立完整的專案治理

[既有使用者更新](updating.md) · [手動後備](manual-setup.md) · [完整回饋範例](user-feedback-examples.md) · [English](../en/windows-example.md) · [简体中文](../zh-CN/windows-example.md)

你已經在 Codex 中推進專案。TaskCarry 為既有工作增加一個獨立治理視窗：記住有效決定，理解進展，把共同約定送回相關視窗，並儲存可恢復的專案記憶。你仍在原來的視窗做事；是否讓治理長期承擔專案協調，由你選擇。

下面以「USB 資料擷取與曲線顯示工具」為例：韌體側提供模擬讀值，電腦側解析、顯示曲線並匯出 CSV，模擬檢查正常、斷線和重連。你可以換成自己的專案，也不必為安裝而新增固定數量的專業視窗。

## 1. 開啟治理資料夾，傳送一條提示詞

建立本機 `TaskCarry` 資料夾，把[完整產品套件](../../START_HERE.md#download)解壓縮到 `toolkit/`，保留套件內版本目錄。在 Codex 中開啟外層 **TaskCarry 資料夾**並建立獨立治理對話。業務檔案留在原位置；已有治理的專案使用[更新入口](updating.md)。

```text
TaskCarry/                 在 Codex 中開啟的治理工作目錄
  toolkit/                 解壓縮後的產品套件
  runtime/                 由助手準備的獨立執行環境
  .taskcarry/              持久專案狀態、物件與工作台入口
  .agents/skills/          本專案使用的治理方法
  .codex/config.toml       專案連線設定，保留其他設定
```

<a id="install"></a>

替換方括號，傳送下面這條完整提示詞。除此之外的設定由治理帶著完成：

> 請把這個對話建立為我既有專案的 TaskCarry 治理總控，核心職責是專案記憶與治理。產品位於：[含 START_HERE.md 和 packages/ 的解壓縮目錄]。專案線索是：[既有目錄、對話或簡短目標；範圍未定時請先幫我整理候選]。
>
> 先讀產品入口、taskcarry-project-setup Skill 及其引用資料，再檢查既有安裝、治理、任務、目錄和 Git。繼承有效決定、成果、任務關係、暫停位置與未提交工作，復用既有設定，不重新初始化既有專案。
>
> 先向我說明你理解的目標、目前進展與建議接入範圍。範圍未明確時，只根據目前工具可見且獲准的索引與目錄整理候選；選定後再讀取相關內容，不掃描無關歷史。已確認事實與建議分開；讀不到原對話時，指導原視窗給出最小交接，不假裝已理解。舊資料可作為參考來源，不必把它們都變成工作視窗。
>
> 根據既有對話建議分工，保留原任務身分與職責。為每個活躍視窗落實實際工作目錄、本機 Git 工作或儲存位置和寫入邊界；復用既有儲存庫與核實的作者設定。把 MCP、Skills 和目前工作入口接到同一個治理，保留專業說明及其他設定，並讓每個視窗分別核對自己的真實連線、原任務、進度與共同約定。我仍可直接在專業視窗推進，不要求所有行動經過總控分派。
>
> 完成本機治理版本儲存，登記官方更新來源並檢查一次；發現新版本先判斷是否適用，不自動安裝。建議每天一個上午報告時段和一至兩個吸收進展時段，與我確認時間和時區後建立或復用原治理對話的原生自動化，不改變模型和權限。
>
> 做完第一次治理：梳理決定、依賴和未完成工作，核對問題、修正與實際效果，把需要更新的共同約定送到相關視窗並核對它們讀到的內容。確定必要狀態、物件、Git 歷史與未提交變更、專案材料和能力版本的恢復範圍，製作本機恢復集並獨立恢復驗證，恢復副本保持待機。網路硬碟或私有遠端由我選擇，上傳、下載與恢復分別驗證。
>
> 按產品的完整治理驗收清單補齊必要設定。需要我信任目錄、重新載入、登入或決定範圍時，只告訴我目前需要的操作和目標，之後繼續核對。最後用自然語言給出專案理解、各視窗職責、實際完成與缺口、下一步建議；技術證據作為可查附件。區分設定完成、自然定時觸發、AI 實際執行和報告送達。中斷後保留原身分，先檢查實際效果，只補缺少的步驟。長期專案協調是否交給總控，由我選擇。

## 2. 由治理帶著完成接入和第一次治理

治理先說明範圍與理解，讓你確認遺漏或歸類錯誤。一個現實專案可以跨目錄、儲存庫與歷史對話；名稱相似不等於同一任務。下面是本例會得到的具體安排：

| 既有工作 | 治理整理出的職責與下一步 |
|---|---|
| 韌體與協定對話 | 明確 `READ,42,1000,1.234` 的欄位與換行規則，儲存三筆穩定模擬輸入。 |
| 電腦軟體對話 | 用同一輸入接通解析、曲線和 CSV，逐項核對輸出。 |
| 模擬驗證對話 | 先驗正常資料，再重播斷線與重連，確認不造資料、不重複舊點。 |
| 舊硬體與介面筆記 | 作為來源繼承有效約定，不算活躍視窗、不重開已完成工作。 |

這些職責可以按既有視窗合併，不要求新建三個視窗。真實裝置測試單獨安排，本例先用模擬資料。治理應同時完成以下工作，而不是只給你一份待辦清單：

- 保留各視窗的原任務、進度、專業說明和未提交工作，明確實際目錄、Git 儲存位置及並行邊界。沒有合適工作目錄的視窗，由治理指導完成實際關聯或在正確位置接續；每個視窗不需要一個新 GitHub 帳號。
- 準備同一治理的連線與工作入口，由每個活躍視窗實際呼叫原生工具並確認讀到的目前約定。設定已產生、入口已發布和視窗已讀到分別核對。
- 完成本機 Git 儲存、官方版本檢查、第一次治理、恢復涵蓋說明和獨立恢復演練。一般資料可留原位，但必要材料要明確納入恢復範圍，憑證另管。
- 完成一個上午報告加一至兩個吸收時段的設定與回讀。時間及時區由你確認，原生信任或登入等必要操作才交給你。

本機 Git、定時設定、更新檢查和首次治理是標準設定。網路硬碟與私有遠端是可選儲存位置，拒絕它們不會製造缺口。遇到宿主限制時，總控只指出目前需要你做的動作。詳細指令放在[手動後備](manual-setup.md)。

## 3. 複核完成報告，按原習慣繼續工作

不需要記住特殊的「完成口令」。總控依據實際驗收給出報告。下面是假設必要設定均已通過的回饋範例，不是某次真實安裝回執：

> USB 資料擷取專案的治理設定已完成。原有韌體與協定、電腦軟體、模擬驗證工作均已接入，舊硬體筆記僅作參考。共同約定是先用模擬讀值打通 USB 序列埠資料格式、曲線與 CSV，無線和實物測試不在本次模擬驗證內。
>
> 各工作視窗分別核對了真實連線與目前工作入口。本機版本儲存、首次治理和獨立恢復演練已通過；恢復副本保持待機。官方更新來源已檢查。上午報告及下午吸收時段已設定並回讀，首次自然觸發尚待驗收。
>
> 現在回電腦軟體視窗，用三筆輸入完成曲線與匯出檢查；模擬視窗再核對正常、斷線與重連。你可以直接繼續開發，我會持續吸收相關進展。治理已建立，不表示工程任務全部完成。

有缺項時，報告要寫「設定進行中」，說明已完成內容、準確缺口和下一步。**設定完成**與**自然定時閉環已驗證**分開：後者須等實際到點觸發、原對話 AI 執行，且報告時段確實送達。手動執行不能代替。

以後可以直接說「繼續原任務」「儲存這個暫停點」或「這次修改影響哪些視窗」。中斷時說：**「從原驗收清單和原任務續辦，先核對實際效果，只完成缺少的步驟。」**

<details>
<summary>驗收依據與技術明細</summary>

完整設定使用 `complete_v1`：選定來源與有效決定、活躍視窗身分和原生連線、目前入口及讀取證據、本機 Git、官方更新檢查、第一次治理、恢復與定時設定均須滿足。`complete_governance_ready` 不替代 `natural_trigger_verified` 或 `closed_loop_verified`。入口來源變動、回執未完成或設定被改動都要準確報告。

每個視窗的原 task/chat、cwd/Git、checkpoint、view 及消費證據，和恢復清單、套件身分、時段回讀均保留供核對。使用者無需在主流程中抄寫這些欄位；具體呼叫見[治理 API](../GOVERNANCE_API.md)。

</details>
