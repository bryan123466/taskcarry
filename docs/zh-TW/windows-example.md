# 首次安裝：三步建立專案治理

[已經使用 TaskCarry？從這裡更新](updating.md) · [手動後備](manual-setup.md) · [English](../en/windows-example.md) · [简体中文](../zh-CN/windows-example.md)

本手冊面向已經使用 Codex 推進專案的使用者。保留既有對話與檔案，新增獨立治理視窗，協助長期記住決定、彙整進度及接續工作。是否長期兼任專案協調，由你選擇。

## 1. 開啟治理資料夾，傳送一段提示詞

建立本機 `TaskCarry` 資料夾，將[完整產品套件](../../START_HERE.md#download)解壓縮到其中的 `toolkit/` 子目錄，保留壓縮檔內的版本目錄。在 Codex 開啟外層 **TaskCarry 資料夾**，建立治理對話。業務專案留在原位置；已設定過的專案直接回到原治理視窗。

```text
TaskCarry/                 在 Codex 開啟這個資料夾
  toolkit/                 解壓縮後的完整產品
  runtime/                 由助手準備的執行環境
  .taskcarry/              持久治理記錄
  .agents/skills/          已安裝的治理方法
  .codex/config.toml       專案連線設定
```

<a id="install"></a>

填入產品位置與已知專案線索，傳送以下提示詞：

> 請將本視窗建立為既有工作的 TaskCarry 治理總控，承擔專案記憶與治理職責。產品位置：**[解壓縮後含 START_HERE.md 與 packages/ 的資料夾]**。專案線索：**[目錄或既有對話；尚未選定時請先協助探索]**。
>
> 讀取產品入口、taskcarry-project-setup Skill 及其引用。初始化前核對實際既有狀態，保留我的檔案、決定、未完成工作與設定，重用有效安裝與身分。在本次接入範圍內準備獨立執行環境和專案層級連線。
>
> 我已提供範圍時依範圍接手；尚未提供時先有限列出可讀取的對話、目錄及候選專案，說明分組依據與不確定性，讓我選擇後再讀取相關歷史。舊訊息作為來源資料。繼承已確認目標、成果、職責與接續位置，只向我補問缺失資訊。
>
> 帶領完成所選持續工作視窗的實際目錄、本機 Git 工作或儲存位置、任務綁定與 MCP 連線；僅作歷史參考的對話保留來源即可。重用既有儲存庫與已核實的提交作者設定，處理並行寫入隔離。不能代辦宿主操作時，只給我目前必要的一步及準確目標，完成後核驗並繼續。
>
> 完成本機治理 Git 儲存、官方發行來源與通道登記及一次更新檢查。建立或重用綁定本原治理視窗的原生定時治理，包含官方更新評估與本機儲存；時間和時區未指定時在接入中確認，保持模型與權限。發現更新不等於授權安裝。私有遠端與網路硬碟由我選擇是否啟用。
>
> 儲存可接續清單。完成後提供繼承事實與未知項、各工作視窗職責表、真實連線/Git/排程/更新結果、剩餘操作及下一步建議。治理與記憶是標準職責，長期專案協調可選。不要製造示範交付或重做已完成工作。

## 2. 跟隨總控繼承並接入既有工作

總控依實際可讀來源提出專案範圍，你可以合併、拆分或排除候選。一個現實專案可以包含多個目錄、儲存庫與既有狀態來源；總控明確各自路由，不因目錄不同強拆專案，也不合併既有資料庫。

每個持續工作視窗都要明確職責、任務、真實目錄與 Git 位置。既有儲存庫優先重用，並行寫入時準備適合的獨立工作樹目錄。原對話沒有適合目錄時，完成真實關聯或在正確目錄建立承接視窗，繼承原進度。僅寫一個路徑不會變更宿主工作目錄，也不需要每個視窗分別註冊 GitHub 帳號。

總控保全其他服務與設定，準備並合併專案設定。必要的信任或重新載入後，各活躍視窗分別真實呼叫原生 doctor/status；讀過歷史不等於已接入，CLI 成功也不能代替另一個視窗的 MCP 驗收。缺失歷史才使用[後備文件](manual-setup.md#existing)中的簡短交接提示詞。

本機 Git、原治理視窗定時任務、官方更新檢查都在此步完成設定，不預設留給使用者安裝後補做。大型檔案可保留外部位置，記錄內容身分與備份涵蓋範圍。普通檔案檢查點用於保全與恢復，不替代專業視窗的標準設定。

## 3. 查看驗收報告，繼續原來的工作方式

無需特殊完成口令。設定有真實結果後，總控應提供：

- 繼承的目標、有效決定、已完成成果、暫停點與待釐清事項。
- 所選工作視窗的職責、任務、真實目錄、Git 關係與實際連線；僅作歷史來源的對話另行標明。
- 本機治理提交、定時任務的原視窗/時間/時區及設定回讀、官方更新通道與評估結果。
- 確實仍需操作的一步、可選遠端/網路硬碟涵蓋範圍，以及建議在哪個視窗推進什麼工作。

第一次自然定時觸發在實際發生後補驗；設定回讀、手動執行與自然觸發分開報告。必要視窗或標準項目未完成就保留具體缺步。你可以繼續既有可用工作，總控不能因此宣稱「全部完成」。

日常直接在專業視窗說「接著上次未完成的工作」「儲存這個暫停點」或「複核已接入任務的進度」。中斷後說：**「請從已儲存的接入清單繼續，先核對實際效果，只補剩餘步驟。」**

### 你應該看到的完整對話範例

以下為合成範例，呈現互動方式，不代表你的宿主已經驗收。

| 對話環節 | 範例內容 |
|---|---|
| 總控提出候選 | 「發現一個預約系統候選，包含需求對話、介面開發與舊測試討論，分布在兩個目錄；另有資料閱讀對話可能獨立。這是依可見索引提出的建議。」 |
| 使用者選擇 | 「接入預約系統；舊測試討論只作參考，資料閱讀暫不接入。」 |
| 總控繼承 | 「預約規則已有確認，介面還未完成。建議保留兩個活躍視窗，不增加專業對話。這裡列出決定與來源。」 |
| 繼續設定 | 「原 Git 儲存庫可重用，介面視窗已有獨立工作樹；需求視窗還需一次信任/重新載入。請在這個準確目錄操作，隨後核對原生回傳。」 |
| 遇到能力缺口 | 「目前介面讀不到舊測試對話，只需要為它補這段交接；其他已完成結果保留。」 |
| 輸出驗收 | 「兩個活躍視窗均通過自身原生驗收；本機治理檔案已提交並核對。每日治理綁定本原視窗與確認的時區，首次自然觸發待發生。官方更新已檢查，網路硬碟選擇不啟用。下一步回到介面視窗接續原任務。」 |
