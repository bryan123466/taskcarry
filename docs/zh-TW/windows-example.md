## 1. 建立治理總控視窗

如果這個專案已有有效的 TaskCarry 治理總控，回到該視窗，讓它核對並繼續原接入即可。否則，在 Codex **建立一個新的獨立視窗**，例如命名為「專案治理總控」。原主對話與專業對話繼續保留工作與歷史。

為治理選擇獨立目錄。首次安裝的合成範例為 `C:/TaskCarry/control`，將選定產品 ZIP 解壓縮到 `C:/TaskCarry/toolkit`。RC6 壓縮套件自帶版本目錄，因此包含 `START_HERE.md`、`packages/`、`docs/` 與 `skills/` 的實際產品根目錄為 `C:/TaskCarry/toolkit/taskcarry-0.2.0rc6`，下方提示詞填寫這個實際產品根目錄。新治理視窗開啟 `control`。原業務檔案留在原位置。宿主權限允許時可讓助手準備目錄；需要時查看[手動準備](manual-setup.md#install)。無關專案使用另一個根目錄，已有綁定的 control 不直接搬動。

準備一個專案定位線索即可：專案目錄、相關舊對話的名稱或連結，或者兩者都有。專案中尚無名稱與簡介時再補充；不用先決定任務 ID、分支名稱或專業視窗數量。

<a id="install"></a>

### 傳送一條接入提示詞

替換兩處填寫項，將下面整段傳給治理視窗。安裝與承擔治理職責在同一次對話中完成。

> 請將本視窗建立為這個現有專案的 TaskCarry 治理總控，負責治理與專案記憶。
>
> 專案定位線索：**【專案位置和／或相關既有對話】**。產品解壓縮目錄：**【包含 START_HERE.md 與 packages 的目錄】**。
>
> 請讀取該產品套件的 START_HERE.md、taskcarry-project-setup Skill 及其 references/onboarding.md，核對實際宿主能力、既有安裝與治理登記。如已有有效 TaskCarry 總控/control，直接重用；保留原工作對話、任務身分、檔案與未完成位置。
>
> 定向讀取獲准資料，恢復專案目標、已完成成果、有效決定、原分工與接續點。將確認事實、你的建議與證據缺口分開。透過對話完成獲准安裝與工作視窗接入，維護可接續的清單；無法代辦宿主操作時，只給我目前必要的一步，填好目標位置與內容。
>
> 接入時給我一次專案梳理、分工與下一步建議，新增專業視窗可以為零。說明我可以選擇讓你長期兼任專案協調；保留我直接在各工作視窗推進的方式，不把這次建議視為持續派工或定時排程授權。
>
> 最後完成一次有限複核，說明繼承了什麼、實際安裝與連線情況、剩餘缺步、各視窗如何讀取與儲存相關進展，以及我的下一步。不要為了接入製造範例交付，也不要重做已完成成果。

**已經進行到一半時：**直接說「請從儲存的清單繼續接入」。治理核對實際結果後補齊缺步；待重新載入不需要再貼角色提示詞或重新安裝。

## 2. 由治理帶著接入既有工作

治理先核對既有情況，再帶領完成剩餘設定。治理目錄為空，不代表業務專案是新專案。確實沒有舊成果的新專案，也可以在同一對話中梳理目標，並在核對後建立起始基準。

<a id="existing"></a>

### 保留原視窗、成果與決定

第一份接手摘要應列出既有成果、有來源的有效決定、任務與負責人、暫停事項與下一步。已接收成果維持歷史事實；新的理解建議先作為候選，確認相關修訂後才成為有效稿，不悄悄覆蓋原決定。

治理只使用實際可存取且與專案相關的上下文。無法直接讀取某個舊視窗時，它會準備一段最小交接提示詞；[手動後備](manual-setup.md#existing)保留了拆開的轉交步驟。它不會掃描全部私人對話，也不承諾持續監控所有視窗。

分工依實際需要提出。一個原工作視窗加治理視窗就可能足夠。只有獨立成果、並行價值、檔案歸屬與相依關係確有需要時再增加專業視窗。多個舊視窗共用目錄時，先核對活躍寫入者並保全現有工作，再調整歸屬或分離工作區；更改對話名稱不會隔離檔案寫入。

<a id="mcp"></a>

### 完成實際工具連線

同一專案的各工作台使用同一個 control。治理為各工作台產生正確執行環境、已登記任務與工作區對應的接入資料及四項 Skills；資料可放在工作台目錄，MCP 仍綁定原 control，不在每個工作區再初始化一個資料庫。

助手把產生的服務合併到目標目錄的 `.codex/config.toml`，例如治理使用 `C:/TaskCarry/control/.codex/config.toml`，並保留原設定。讓目標 Codex 聊天開啟或選用同一目錄，完成必要的專案信任，再使用宿主支援的操作重新啟動/載入 MCP。另一目錄的設定不會讓目前聊天自動連線。宿主動作需要你操作時，助手給出目前一步，收到回覆後繼續。[手動設定與驗收](manual-setup.md#mcp)提供準確位置、官方依據與後備步驟；setup 本身不啟用宿主。

連線結果分為三項：**資料已產生、宿主已載入、該視窗原生 doctor/status 呼叫成功**。隔離 CLI 成功可作為後備證據，不能代替原生 MCP 成功。治理記錄實際版本、解譯器、模組及 control/任務綁定；一個視窗成功不表示另一個視窗也已載入。

## 3. 按原來的習慣繼續推進

你可以直接在原有或協商新增的專業視窗工作。在有意義的暫停、成果或決定變化處，由助手儲存相關進展與下一步；接續前讀取目前任務及相關有效決定。治理彙整已接入的證據並核對缺口。共享進度不會自動合併所有工作區的程式碼。

可以說「繼續上次未完成的工作」「儲存目前暫停位置」或「整理已接入任務的目前進度」。穩定 Git 階段可單獨交付，未完成工作繼續保留。普通文件 checkpoint 無需 Git，儲存的是選定檔案；完整的非 Git 成果交付與接收合同仍是後續能力。

| 工作方式 | 治理負責什麼 | 你怎樣工作 |
|---|---|---|
| 治理與記憶，預設 | 來源、有效決定、任務進展、接續與有計畫的成果接收 | 直接在工作視窗推進，按需找治理。 |
| 兼任專案協調，可選 | 上述記憶，加優先順序、相依關係與分工建議 | 可以在總控討論整體安排，也繼續在其他視窗工作。 |

這項偏好可調整，不需要重建專案。首次專案梳理不會自動開啟持續協調或排程任務。

<a id="check"></a>

### 接入完成時應該看到什麼

- 繼承的目標、決定、任務、既有成果與未完成位置清楚，建議與未知仍有標示。
- 唯一 control 及需要時的接收基準明確，原工作與使用者設定得到保全。
- 實際安裝、每個宿主連線與剩餘動作分別有證據。
- 各工作視窗知道怎樣讀取相關上下文、儲存進展與接續；新增專業視窗可以為零。
- 首次有限複核報告實際結果或就緒狀態。checkpoint 不等於交付，接收不等於業務驗收，計畫不等於已經執行。

### 按需增加的能力

定時治理是可選項。需要時，治理重用首次複核結果，透過宿主實際排程能力設定；儲存提示詞不等於已驗證自然觸發。詳見[定時治理](automation.md)。

<a id="private-git"></a>

[私有 Git 與備份](remote-and-multicomputer.md#private-git)只涵蓋實際納入並核實的內容。記錄路徑不等於備份，普通 Git 推送不會自動儲存線上 control 資料庫或全部未提交工作。

<a id="multi-computer"></a>

[多電腦協作](remote-and-multicomputer.md#multi-computer)需個別驗證。本版不提供自動主節點選舉或共享資料庫多方寫入，接通 MCP 也不代表所有平台與多機流程已經完成。
