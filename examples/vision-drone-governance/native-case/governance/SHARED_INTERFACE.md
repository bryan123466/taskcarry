**版本 `rc8-indoor-replay-v1`**。首阶段使用合成帧与预置事件做室内固定障碍离线演示，室外与实飞留作后续。本协议中的字段、节拍和界面预期是治理为本轮选定的联调口径，专业结果以各窗口实际运行回执为准。

## 数据与时间

- `ticks` 按 `tick` 从 0 连续递增。每拍带一个从回放起点计的整数 `timestamp_ms`。本轮选名义 `15 fps`，每拍时间按 `floor(tick × 1000 / 15 + 0.5)` 单独取整，依次为 `0、67、133、200、267、333 ms`。算法旧样例的 `40 ms` 间隔留在原文件及原测试中。
- `input_profile` 的 `640×480 RGB24` 用于说明合成输入口径。回放文件含帧元数据与预置事件，显示和测试可逐拍单步推进。`timestamp_ms` 仅用于本轮合成序列。硬件的 `capture_time` 提案与采集延迟测量留作后续。
- 每个收到的帧在 `frame` 中给出本次回放唯一的 `frame_id`、`processing_status: "ok"` 和 `events` 数组。事件恰有 `frame_id`、`label`、`region`、`confidence`、`timestamp_ms`。事件的帧号和时间与外层帧和节拍核对。同一帧可有多个事件。
- `label` 使用 `wall`、`column`、`box`，分别显示为「墙面」「立柱」「箱体」。原软件的「围挡」留在原示意，新版本按三项字典校验。`confidence` 是 `[0,1]` 内的人工样例分数，本轮显示逻辑保留所有候选。
- `region` 表示未裁切整帧内的归一化轴对齐框，左上为原点，横轴向右，纵轴向下。要求 `0 ≤ x_min < x_max ≤ 1`、`0 ≤ y_min < y_max ≤ 1`。令 `cx = (x_min + x_max) / 2`，用 `cx < 1/3` 显示 `left`（左侧），用 `1/3 ≤ cx < 2/3` 显示 `center`（中部），用 `2/3 ≤ cx` 显示 `right`（右侧）。跨区的框仍按中心归入一个区，等于边界时进入右边相邻区域。

## 回放状态与预期观察

收到 `frame` 且 `processing_status` 为 `ok` 后，将连续缺帧计数清零。`events: []` 表示成功处理的空帧，界面显示「本帧无候选」。`frame: null` 表示此拍没有帧交付，连续缺帧计数加一并清除当前候选显示。第一次缺帧保留模拟连接，显示「等待新帧」。第二次进入模拟断流。下一帧到达即恢复连接。格式错误应报告输入问题。本样例覆盖成功处理和人为断流，处理失败、乱序与队列溢出的行为待另行验证。

初始链路状态为 `waiting`。候选日志按节拍、帧内数组顺序累加。连接状态变化用独立记录或可区分的类型 `connected`、`disconnected`、`reconnected`。等待拍和空帧不增加候选条目。

| 拍 | 相对时间 | 帧 | 预期界面 | 链路变化 |
| --- | ---: | --- | --- | --- |
| 0 | 0 ms | `indoor-000` | 左侧墙面，已连接 | `connected` |
| 1 | 67 ms | `indoor-001` | 中部立柱、右侧箱体，两个候选共享帧号 | — |
| 2 | 133 ms | `indoor-002` | 本帧无候选，链路已连接 | — |
| 3 | 200 ms | 无 | 等待新帧，链路已连接 | — |
| 4 | 267 ms | 无 | 模拟断流 | `disconnected` |
| 5 | 333 ms | `indoor-005` | 左侧箱体，链路恢复 | `reconnected` |

本文件的逐拍预期为 6 拍、4 个收到的帧、4 条候选、1 个空帧、2 拍连续缺帧。计数用于核对可重现的界面和数据行为。样例分数来自人工设定，真实识别、实时吞吐、硬件资源与飞行能力的证据有待另行获取。

## 四个窗口的验收

| 职责 | 专业窗口需要实际核对的内容 |
| --- | --- |
| 软件 | 用同一个 JSON 在本地浏览器运行监控示意。从重置到最后一拍，核对三区映射、同帧多条、空帧、两个缺帧、状态恢复与日志。 |
| 视觉算法 | 校验帧号关联、节拍、类别、边界框、候选分数与空帧。实际运行边界映射和一项非法输入测试，记录观察结果。 |
| 硬件方案 | 从实际回放文件复算节拍、两次未收到帧及恢复，核对模拟时钟和输入口径。采集时间、延迟及资源只记录其当前证据。 |
| 产品与演示 | 用同版本、同摘要的技术回执复核可公开分享的表述及操作步骤。每项对外事实引用具体已通过检查。证据欠缺的部分留在内部待办。 |

三个技术窗口各自保存 `software-evidence.json`、`algorithm-evidence.json` 或 `hardware-evidence.json`。每份包含 `role`、`replay_version`、`fixture_sha256` 和 `checks`。每项检查写入 `id`、`status`（`PASS`、`FAIL` 或 `PENDING`）、`expected`、`observed`、`reproduce`，后两项用于说明实际观察和复现方法。尚未运行可将 `observed` 写为 `null` 并说明待核事项。预期表只作比对。
