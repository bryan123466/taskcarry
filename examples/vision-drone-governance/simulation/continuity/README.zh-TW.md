# 對話無法繼續時，讓原任務在新對話中接著推進

無人機演算法已完成，軟體也整合了確切的偵測器。若原演算法對話不能再工作，新對話能否依專案記憶接續？這次演練將原視窗受控轉為停寫，由治理在需要時才建立接續視窗，沿用原任務、目錄、檢查點與成果，繼續一項具體的邊界驗證。

本次沒有刻意觸發 Codex 當機或上下文壓縮故障，而是模擬舊對話不能再負責寫入，檢查工作能否由視窗外的記憶接續。第一次配置時也沒有預先建立空白備用視窗。

## 先保留工作，再切換視窗

原對話結束自己發起的驗證，留下停寫回執。治理核對宿主回合已結束、沒有該視窗的進行中寫入，再記錄 Git HEAD、索引、已保存檔案與未提交改動。原對話、已完成的演算法和原檢查點保留不動。

治理為同一演算法任務發布交接：舊視窗保留歷史且唯讀，新視窗確認入口後負責這次有限的新工作。新視窗用真實宿主身分找到路由，讀取同一 control 與原任務，自行呼叫原生 MCP 並登記入口消費。配置檔或別人替它填寫的「已接入」，不能代替這些實際讀取。

接續只讀使用[已交付的偵測器](../app/detector.js)，不重新初始化專案，也不複製另一套演算法混用成果。

## 下一步是可驗證的工程工作

待辦是檢查偵測器「至少 16 像素、四連通」的規則。新視窗依原[介面契約](../INTERFACE_CONTRACT.json)獨立撰寫驗證，輸入三張 160×120 RGBA 合成影像。三幀的中繼資料、背景與演算法相同，只變更指定像素。

| 輸入 | 邊界條件 | 預期結果 |
| --- | --- | --- |
| A：3×5 的箱體色矩形，共 15 像素 | 小於門檻 | 有效幀，零偵測 |
| B：A 加一個共邊像素 | 連通區域達 16 像素 | 恰好一個箱體，像素數為 16 |
| C：A 加一個只在角上相接的像素 | 同色總數 16，四連通分量為 15 與 1 | 有效幀，零偵測 |

新增工作保留輸入摘要、實際輸出、重現命令及偵測器前後摘要。實際成果見[邊界驗證](boundary-evidence.json)與[驗證腳本](verify-boundary.cjs)。

## 已確認的進度

| 步驟 | 實際狀態 |
| --- | --- |
| 原視窗停寫，原任務與目錄保留 | 已有回執且經治理核對 |
| 在既有專案按需建立新對話 | 已完成 |
| 為同一原任務發布兩個視窗入口 | 已完成；原入口及歷史回執保留 |
| 新視窗原生連線、讀取與消費 | 已完成並保存原生回執，見[連線摘要](native-acceptance.json) |
| 三幀邊界檢查及原檔案保全 | 三幀均通過；原檔案與 Git 狀態保留 |
| 舊視窗再讀交接並保持唯讀 | 舊視窗已唯讀回看交接與新成果，未重跑或新增消費 |
| 治理核對並保存新成果 | 已完成；保留原任務與檢查點，保存核驗摘要 |

[接續證據](continuity-evidence.json)記錄了本次有限演練的完成結果。治理交叉核對新視窗自身消費、三幀通過結果、舊視窗唯讀回報、原 Git 狀態及四份歷史設定前像。原業務任務仍停在原有 waiting 檢查點，沒有把本次核驗視為整個專案驗收。舊視窗依要求未新增 Core 消費紀錄：其 `NOT_VERIFIED` 消費狀態，與已完成的宿主唯讀回報分別記錄。

## 使用者會收到的指引

以下是方法的使用者側範例，不是實際對話的逐字引述：

> 原演算法工作已保存在專案，會沿用原任務及檢查點。我先確認舊視窗和它啟動的背景寫入已停止，再準備交接。請在原演算法專案中建立一個新對話；舊對話保留供參考，不需要重新安裝或搬走檔案。新對話核對自己的 MCP、原任務及當前入口後，就接著完成 16 像素邊界驗證。我會把它交回的結果納入專案記憶。舊視窗若恢復，先讀交接並保持唯讀，避免兩邊重複寫入。

若宿主需要信任專案、開啟目錄或重新啟動，治理應提供確切位置與有限操作，已完成並驗證的步驟不重複。接續內容來自已保存的成果與檢查點，不憑空補出遺失的對話內容。

**換一個對話，已保存的專案記憶、任務身分與成果仍可接著用。** 這不會修復宿主，也不保證找回未保存或從未讀到的上下文。TaskCarry 路由負責入口，單一寫入者仍依賴實際停寫與職責交接，不是強制撤銷舊對話的檔案權限。

```sh
node continuity/verify-boundary.cjs
```

複製 simulation 目錄後，以 Node.js 24 執行。可攜腳本只讀固定應用與契約，新結果僅寫入 `continuity/local/`。它重現像素邊界檢查，不重做宿主對話交接。
