# RC8 仿真原型验收计划

技术验收覆盖真实生成像素、检测、命令、仿真结果和用户操作。宿主验收覆盖原治理、四个专业原窗口和新增独立测试窗口的原生调用，以及治理与测试在同目录的不同任务路由。当前技术项目均待实现或实测。原治理的候选原生 `doctor` 与 `status` 已实际通过。 [接口合同](../INTERFACE_CONTRACT.json) · [原治理原生回执](../README.zh-CN.md)

## 独立技术用例

| 检查 ID | 操作和通过条件 | 最少证据 |
| --- | --- | --- |
| `SIM-OFFLINE` | 从独立目录以桌面 Chrome 的 `file:` 打开交付页面。选择三个场景，启动、暂停、恢复、重置。暂停期间跨过两个逻辑间隔后，拍号和日志长度稳定。重置回到场景起点、等待状态和空日志。运行时无外部请求及页面异常。 | 浏览器版本、资源请求和异常记录，操作前后可比状态。 |
| `SIM-CLEAR` | `clear-room` 首帧为有效空画面，检测 `ok` 且列表为空。四步 `MOVE_N` 到达 `(4,2)`。终止拍为 3，结果为 `arrived`，碰撞为 0。 | 同一回合的帧摘要、检测、动作和导出轨迹。 |
| `SIM-DETOUR` | `fixed-obstacle` 首帧从像素提取墙面、立柱、箱体。箱体占用 `(dx=0,dy=-1)`，第一步 `MOVE_E`。终止拍 5 到达，轨迹与合同一致，碰撞为 0。 | 实际画面、检测框、首拍命令、完整轨迹。 |
| `SIM-DROP` | `drop-and-recover` 在拍 1、2 无帧，命令均为 `HOLD`，位置及访问计数保留。拍 2 记录模拟断流，拍 3 收到有效帧后恢复，检测来自当拍。终止拍 7 到达，碰撞为 0。 | 缺帧、连续计数、链路变化、恢复帧及最终导出。 |
| `SIM-PIXELS` | 对合同的同一 `clear-room` 初始帧做隔离 A/B。保持帧号、时标、姿态、目标、到访计数和仿真场景一致。B 仅改前方格像素。记录实际字节差和可读摘要。A 的 `ok + []` 得 `MOVE_N`，B 的箱体检测得 `MOVE_E`。两次都运行同一检测及控制入口。 | 两帧字节摘要、变化坐标、相同非像素输入、实际检测和命令。 |
| `SIM-COLLISION` | 在独立测试中让仿真器处理合同的 `collision_probe`。碰撞位置不前进，状态为 `collision`，后续拍和日志停止。用同一状态呈现逻辑核对碰撞指示。 | 仿真动作前后位置、终态、日志及实际界面状态。 |
| `SIM-INVALID` | 向检测入口提供尺寸、像素长度或帧号有误的帧，实际结果为 `invalid`、空检测和 `HOLD/invalid_frame`。状态可辨认。 | 一份确切坏帧输入摘要及实际控制结果。 |
| `SIM-TIMEOUT` | 通过已有测试入口给同一仿真连续不可用帧。确认恰有 12 条记录，末拍 `tick=11`，终态 `timeout`。继续等待，日志保持 12 条。重置后用正常输入运行同一原场景并到达。 | 注入方式与实际原输入、超时导出、等待前后日志条数、重置后的正常完成记录。 |
| `SIM-EXPORT` | 三个场景各从重置后独立运行两次。导出文件能解析，版本、场景、帧摘要、时标、动作、轨迹、碰撞和到达结果稳定。渲染层的播放等待不改变逻辑时间。 | 两轮导出和逐字段对比，记录用到的文件及 SHA-256。 |
| `ENG-DOCS` | 工程资料包含真实模块分解、数据方向、接口与时序、资源预算、接线规划和后续实测清单。示例 RGBA 帧 `76,800 B`，名义 `10` 拍/秒下 `768,000 B/s`。两帧缓冲 `153,600 B`。供电、电平、接地、传感器与执行机构的具体参数待选型核对。 | 三份工程文件与算术依据。将推算与实测列明。 |
| `PRODUCT-EVIDENCE` | 三份产品稿均可按脱敏后的离线包使用。每项已实现表述能映射到通过的检查和实际证据。合成图像、软件运动及工程估算的范围清楚。 | `product-claims.json` 与复演记录，保留未通过和缺失项。 |

独立报告逐项留 `id`、`status`（`PASS`、`FAIL` 或 `PENDING`）、被测版本及文件摘要、实际输入、预期与观察、复现方法。研发自测可作补充，最终技术结果使用独立窗口的运行证据。

## 原生 MCP 与同目录验收

每个窗口实际调用自己可见的 `taskcarry_rc8` 原生 `taskcarry_doctor` 与 `taskcarry_status`。根据返回确认 `0.2.0rc8`、`work/rc8-c3aac797-runtime` 的解释器及模块目录、原治理 control、项目来源和原任务最新检查点。磁盘来源摘要期望为 `e1c8571120eea9eaaea60891a7cabef51cef1ab0e5c276d32318ae18262e6b90`。`doctor` 的来源摘要是磁盘口径。各窗口的真实回执包括实际 `thread_id`、`cwd`、`transport=native_mcp`、原始结果和入口匹配。工具缺失时记录原始提示及当前待办。

| 窗口 | 应核对的任务 | 当前记录 |
| --- | --- | --- |
| 原治理 | `rc8-governance` | 本原聊天实际调用 `doctor`、`status` 成功，运行时、来源和原 control 匹配。`status` 未列该治理任务的检查点，读回四个专业任务的既存检查点。 |
| 软件 | `drone-software-monitor` | 等此原窗口实际回执。 |
| 视觉算法 | `drone-vision-events` | 等此原窗口实际回执。 |
| 硬件方案 | `drone-hardware-concept` | 等此原窗口实际回执。 |
| 产品与演示 | `drone-product-demo` | 等此原窗口实际回执。 |
| 独立测试 | `drone-independent-test` | 同目录真实窗口已确认。登记前已在该窗口原生调用 `doctor` 和 `status` 且匹配候选。任务路由及消费由登记后的该窗口核验。 |

同目录接入以真实的两个聊天 ID 按以下步骤验收。登记与发布的实际效果见本轮共享接入回执。

1. 主工作台在同一已信任治理项目、同一根目录创建测试聊天。核对其真实 `thread_id` 与实际 `cwd`，检查与原治理的 ID 不同、目录相同。
2. 用一个已注册的真实 Git 目录工作区代表该目录。如无现存同根登记，建议名称 `governance-shared`。原治理保留 `rc8-governance`。收到新窗口真实身份后登记 `drone-independent-test`。候选的共享路由要求明确的目录级材料。如需转换，先审阅 `setup` 的 `mode: "preview"` 和 `binding_mode: "directory"`，`target` 为原治理根目录并指定工作区，目录绑定省略 `task_id`。只处理目录级缺项，保留现有候选运行时及四专业窗口。
3. 上述前提满足后，按候选支持的 `workbench plan`、`routing: "shared"` 提出同一工作区的两条精确聊天路由，分别绑定原治理任务与独立测试任务。同一目录沿用一份项目级 MCP 服务配置，两个聊天分别实际调用。计划前核对新 ID 和明确来源。保留旧视图，按后续约定核对计划效果。
4. 两个原窗口分别用实际 ID 读 `taskcarry_workbench` 的 `status`（`routing: "shared"`、`thread_id`）和各自任务上下文。正确结果为同一目录、同一来源、不同聊天与任务，各自读取匹配入口。找不到当前 ID 的路由时记录实际缺口。消费回执按窗口逐份复核。

验收完成需要独立技术运行证据、可复演的公开交付包和六个窗口的原生回执。治理与独立测试已有各自初验，四个原专业窗口仍待原生加载回执。共享路由及消费按实际聊天核验。主工作台负责精确发布。
