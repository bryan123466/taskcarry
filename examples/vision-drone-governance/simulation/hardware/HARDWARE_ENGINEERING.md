# RC8 v2 硬件工程说明

适用范围为室内固定障碍的本地二维合成仿真，任务为 `drone-hardware-concept`。工程口径依据 `rc8-drone-sim-v2` 接口合同（schema 2），合同原字节 SHA-256 为 `77fa7df9dc17bbc95e3a728dd45e68c420dfbabdf770c3ac5ff9c714be025130`。

## 模块与数据方向

| 模块 | 输入与输出 | 职责 |
| --- | --- | --- |
| 相机角色／合成帧源 | 仿真场景、动作前位置和拍号 → `RenderedFrame` 或 `null` | 按当前位置渲染北向固定俯视图。局部视野为 5 × 5 格，中心格为 `col=2,row=2`，每格为 32 × 24 px。完整画面以 160 × 120 RGBA8 输出。场景指定缺帧时交付 `null`。 |
| 采集适配 | 当拍帧与逻辑时标 → `FrameEnvelope` 送入检测 | 用 `scene_id`、`tick`、`sim_time_ms` 和 `frame` 封装采集结果。帧号由场景 ID 和拍号拼接为 `scene_id:tick`，像素为连续的 `Uint8ClampedArray`。 |
| 视觉处理 | `detectFrame(frameEnvelope)` → `DetectionResult` 送入链路管理与决策 | 校验帧号、尺寸、格式和长度。从当拍像素提取声明色的四连通区域，保留至少 16 px 的分量，输出原图归一化半开边界框、相对格坐标和像素数。 |
| 链路管理 | 当拍检测状态 → `link_state`、`consecutive_unusable` 和 `link_event` | 根据 `ok`、`missing` 或 `invalid` 更新连接状态。先完成本拍链路更新，再把状态交给决策。 |
| 决策 | `chooseCommand(controlInput)` → `Command` 送入仿真执行 | 读取当拍检测、更新后的链路状态、动作前位置、目标和 81 项访问计数，输出动作、原因、拍号和来源帧号。障碍信息来自当拍像素检测。 |
| 执行仿真 | `Command` → 新位置、到达或碰撞结果 | 在 9 × 9 网格上执行一格正交移动或保持位置。用场景真值判定命令结果。成功移动才更新到达格的访问计数与轨迹。 |
| 主机界面与日志 | 当拍渲染像素、检测、命令和执行结果 → 显示、`TickRecord`、`Export` | 检测框绘制在呈现层。按拍记录原始像素摘要、位置前后值、检测、链路、连续不可用数、命令及运行状态。导出由起点和成功移动形成的轨迹与有序记录，像素以摘要留证。 |

仿真通过 `globalThis.RC8DroneSimV2` 调用检测与决策入口。渲染和执行模块各自在仿真器内使用场景几何，决策入口的障碍信息来自检测结果。

## 时序、停留与恢复

逻辑拍从 0 开始，`sim_time_ms = tick × 100`。每拍按渲染或缺帧、封装、检测、链路更新、决策、执行、记账的顺序完成。有效帧按原始 RGBA 字节计算 FNV-1a 32 位摘要，记录为 8 位小写十六进制。缺帧和无效帧的 `frame_digest` 及命令的 `source_frame_id` 为 `null`。

`missing` 与 `invalid` 都计入连续不可用数。首次不可用保留已有链路状态，两次连续不可用进入 `disconnected`。收到有效帧后计数清零。

| 当拍条件 | 链路与帧处理 | 当拍动作与记录 |
| --- | --- | --- |
| `ok`，含空检测列表 | 连续不可用数清零。`waiting` 首次得帧记 `connected`，从 `disconnected` 恢复记 `reconnected`。 | 按当拍检测决策。空检测列表表示有效帧，可进入常规决策。 |
| `missing` | `frame=null`，清除当拍候选。 | `HOLD` 保持位置与访问计数。原因通常为 `frame_missing`，当前链路已断开时用 `link_disconnected`。 |
| `invalid` | 帧号、格式、尺寸或像素长度有误。返回空检测及 `error` 并清除候选。 | `HOLD/invalid_frame`，位置及访问计数保持。后续以新的有效帧恢复。 |
| 碰撞、到达或超时 | 碰撞拍位置保持，记 `collision`。到达记 `arrived`。执行 12 拍仍未终止则在索引 11 记 `timeout`。 | 终态写入对应记录，随即停止出新拍。 |

暂停时拍号和日志停留，恢复从原逻辑拍继续。重置回到起点、`ready` 和 `waiting`，起点访问计数为 1，日志清空。对于检测调用抛错或超时一类尚未定稿的处理失败，工程建议冻结当拍移动并记诊断来源。如何映射错误、超时判据和恢复条件仍待软件与算法核对。

`capture_time` 保留为后续采集提案。拟在源帧交付采集适配层、进入等待队列前打点，沿帧标识透传。采集时钟来源、单位、与主机的时间对齐、消费侧接收及显示打点待确认。当前时标由仿真逻辑拍产生。

## 帧负载和缓冲预算

按每像素 4 B、逐行紧密排列，行长度为 **160 × 4 = 640 B**，单帧为 **640 × 120 = 76,800 B**。逻辑间隔 100 ms 对应每秒 10 拍。以每拍一份有效帧估算，名义原始帧负载为 **768,000 B/s**。两份完整原始帧缓冲作为预算假设，像素占用为 **153,600 B**。v1 使用 640 × 480 RGB24、名义 15 fps 和 3 帧等待队列假设，其数字适用于 v1 回放。

双帧估算只覆盖两份 RGBA8 像素。需要在集成测试中测量原帧复制、行填充或格式转换、Canvas 与叠图、检测中间数据、帧封装及日志对象、序列化和运行时分配。后续若采用独立采集链路，链路封装及传输开销也需计量。缓冲生命周期建议由生产方完成写入后交接给读方，等检测和展示所需读取结束再复用。缓冲实际数量、峰值、并发方式和过载处置待测。 [资源预算](RESOURCE_BUDGET.csv)

## 后续台架验证清单

| 待测项目 | 验证方法与所需证据 |
| --- | --- |
| 采集时钟与端到端时延 | 先确定采集回调打点和时钟基准，校核跨端时钟偏差。用帧号关联采集、入队、检测完成、执行结果和显示打点。同一基准下分别统计采集到接收、采集到显示的延迟，记录样本量、分布与峰值。 |
| 实际帧负载 | 采集一段带已知画面和帧号的输入，记录尺寸、通道顺序、实际行步长、帧字节数和单位时间交付字节数，复核行填充和格式转换的开销。 |
| 处理资源 | 同段输入记录渲染／采集、预处理、检测、决策、展示和日志各阶段的耗时，同时测 CPU 占用、峰值内存与额外像素副本。 |
| 缓冲与过载 | 记录逐帧入队、开始处理、回收和丢弃，比较高水位与两份原始帧预算。受控延迟消费后核对帧号、摘要、停留时长及丢弃原因。 |
| 掉帧、断流与恢复 | 注入一拍、两拍不可用及恢复帧。核对连续计数、位置与访问计数、链路事件和恢复后的来源帧号。在合同场景 `drop-and-recover` 中，对照拍 1、2 的 `HOLD`、拍 2 断开和拍 3 恢复。 |
| 处理失败 | 分别注入坏帧号、错误尺寸和错误长度，读回 `invalid`、错误文本、空检测和 `HOLD/invalid_frame`，核对位置、访问计数及下一有效帧。检测调用异常和超时的映射另行验证。 |
| 仿真超时与重置 | 按 `SIM-TIMEOUT` 在仿真测试入口持续注入不可用帧，核对恰有 12 条记录，末拍 `tick=11` 且终态是 `timeout`。继续等待时记录数保持 12，重置后用正常输入复跑同一原场景。 |

以上台架项均待测。选型与物理接口记录见 [概念接线规划](INTERFACE_WIRING_PLAN.md)。
