# Conditional recovery / 条件经验恢复

For a failed full governance cycle, inspect its exact owner/resource reservation and effect records; resume the same identity and verify effects before changing a receipt. Health is multidimensional and expires with its evidence. Unknown or stale is not healthy; one waiting item is not global failure. Question reminders count actual delivery receipts on distinct local dates, never retries or scan appearances. The default unanswered-date budget is two; preserve the question after the limit instead of repeatedly notifying.

For project-level recovery, use the separate `recovery` plan/execute/verify interface. A selected-file `restore` is not a full project restore. Preserve state plus referenced objects, selected history/index/WIP and required external materials in a sealed set. Restore to an independent standby copy, retain the original, inspect disabled host entries and rebind native access. Old executable plans/cycles are historical evidence, not replay instructions. Activate one writer only with an explicit handoff and exact old-replica declaration; the tool cannot independently fence another computer. Keep encryption keys and credentials outside the portable set.

For private publication or static media copying, use exact `transfer` plans. Verify remote effects after a transport failure before retrying; never force an old tag or expand to all refs. A verified copy into a sync folder proves local bytes only. Verify retrieval and isolated restoration before calling it offsite recovery. Tool/package rollback must use a compatible retained environment and current project state; do not restore an old database over decisions created after an update.

Start with the current error code, operation journal and actual Git/file effects. If an effect already happened, preserve that fact and repair only missing bookkeeping. Do not infer absence from a missing receipt, erase old evidence, or repeat the complete workflow.

For interrupted setup or restore, inspect that operation's saved intent and files, then use its own supported continuation contract. Receiving experience actions are not generic restore commands. Preserve user edits and candidate identity; a new package or changed target is not automatically the same retry. Missing host access is an onboarding gap until evidence shows a product failure.

TaskCarry's experience rules are data, not shell programs. `verify_and_finalize` lets the receiving executor verify an already-applied Git effect and finish its receipt. `refresh_plan` is planning advice: where a saved operation proves that no effect was applied and has no candidate or stash, the agenda can return a structured `plan_request` with `execute: false`. It never silently replaces or executes a plan. Review the original failure and changed conditions, request the new plan, then review its exact scope before execution. Bind rules to the observed code and operation; add task scope when the evidence is task-specific. Enabled/version checks and applicability must hold before use.

For receipt recovery, repeat the original bounded governance call so the engine verifies effects and uses an applicable rule. Inspect the returned experience-use and completion evidence. A matching rule, or reading its suggestion, is not proof of a repair. If the effect cannot be established or the condition changed, retain the actionable issue and identify the missing fact. Repeating an unchanged preparation failure is not progress; resolve its concrete conflict or retain its next condition. Do not discard the journal to restart a transaction.

Unknown defects can produce a candidate fix and synthetic regression scenario within authorized development scope. Validate the initial failure, the corrected outcome, replay safety and a negative non-applicable case before proposing a public rule/tool update. Never experiment on a user's live unrelated task. Record whether only scripts, simulated clients or an actual AI/host integration were tested.

For a defect that needs continuing maintenance, use `taskcarry_issue` with a stable condition fingerprint, then `taskcarry_fix` to link the tested fix, version and evidence references. A changed condition reopens review; closing an issue requires a reviewed resolution reference and cannot close an unfinished Git operation. Identical records are reused. The fix result compares actual project setup and disk fingerprints; an installed version match still does not prove that another running host process reloaded it. A shared fix belongs in the tool or Skill release so future work can prevent the failure, not only repair it repeatedly. `taskcarry_upgrade` repairs the derived current-work index for an older store; it does not upgrade the package, install Skills, or change business branches.

Keep fix development, reception, publication, installation, host reload and observed outcome as separate evidence. Record applicable version and actual adoption when available. Writing experience is not installing a fix. Public improvements remove private paths, transcripts and project-specific dependencies and reproduce the condition with synthetic material.

Use `governance` to inspect package, managed-method and user-rule content identities before maintenance. Retain project customizations and tie the review to exact fingerprints; a saved review does not attest host loading. The official `update_check` and explicit `update_assess` distinguish an available release from an applicable repair. A new release, recorded fix, local install and resolved original condition each need their own evidence. A failed network check is unverified, not proof that the installed release is latest.
