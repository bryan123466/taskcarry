# Original-chat governance loop

The complete standard schedule returns to the existing governance chat with its selected runtime, source routes, model and permissions: one daily report and one or two bounded absorption slots. The host provides scheduling and AI. Use native create/view/update capabilities; do not edit scheduler files. Reuse matching slots instead of adding writers. User pause/disable decisions remain effective. Legacy single-slot receipts retain their earlier coverage.

Keep the durable prompt self-contained: source routes, responsibilities, task boundaries, fixed isolated runtime, current workbench entry, official release channel and this method. Verify each slot's time zone, period and purpose. Configuration readback, natural trigger, original AI execution and actual report delivery are separate evidence. A missed period does not require replaying past cycles.

1. Read the current workbench entry and bounded agenda/task context. Start or resume one `cycle` with the existing owner and exact resources. Inspect changed or specifically missing permitted chat/material evidence, using bounded source pages and their continuation. Preserve paused work and effective decisions. Quiet history is not backlog.
2. Retain source revisions and their observed/understood phases. Record facts and judgments separately with revision checks; retain corrections and historical relationships. `observe` keeps existing task/stage links. Freeze a small delivery `run` selection when needed. Inspect actual effects before resuming operations. Receive exact Git stages under an authorized plan; adopt only for a real dependency.
3. Apply condition-bound recovery using the actual error, operation and evidence. A suggestion is not an executed repair. Retain the original issue/fix chain; source fix, release, local installation and effective resolution stay distinct. Do not repeat complete governance to repair one receipt.
4. Publish sourced rules/progress through a `workbench` plan, preserving each task and professional instructions; record consumption separately. Save meaningful local Git changes through exact `preserve` plans. Verify recovery-set coverage and healthy evidence; optional private `transfer` follows its own exact destination plan. No meaningful change means no artificial task, commit or governance version. A reference does not establish a backup.
5. Run update_check for the chosen official stable/RC channel and explicitly retain an update_assess applicability decision. Network failure is unverified. Installation follows maintenance authorization for a concrete object; do not track development branches or install every release automatically.
6. Inspect selected receipts once, record multidimensional health and finish the selected cycle only after its actual effects are terminal; retain unfinished positions otherwise. A report slot delivers a concise project report; absorption slots stay quiet without meaningful change. Record actual report/question delivery separately, and count unanswered questions only on distinct delivered dates (default limit two). Waiting is normal retained work, not failure. A completed batch is not project completion.

Report runtime/method identity separately from custom project rules. Next-work suggestions follow the chosen coordination role. Optional remote/cloud work follows explicit destination/scope and existing authorization. Capture, local validation, upload, download and independent restore have separate results. Never treat a synced live state database or active Git metadata as a sealed backup.
