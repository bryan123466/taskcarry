# Original-chat governance loop

The standard schedule returns to the existing governance chat with its selected runtime, source routes, model and permissions. The host provides scheduling and AI. Use native create/view/update capabilities; do not edit scheduler files. Reuse a matching task instead of adding writers. User pause/disable decisions remain effective.

Keep the durable prompt self-contained: source routes, responsibilities, task boundaries, fixed isolated runtime, record entrypoints, official release channel and this method. Verify time zone and period. Configuration readback, a manual pass and a naturally delivered heartbeat are separate evidence. A missed period does not require replaying past cycles.

1. Read bounded agenda and relevant task context with source-qualified IDs. Inspect only changed or specifically missing permitted chat evidence. Preserve paused work and effective decisions. Quiet history is not backlog.
2. Record changes through observe with the prior revision. Freeze a small run selection when needed. Inspect actual effects before resuming operations. Receive exact Git stages under an authorized plan; adopt only for a real dependency. Shared progress does not merge every branch.
3. Apply condition-bound recovery using the actual error, operation and evidence. A suggestion is not an executed repair. Retain the original issue/fix chain; source fix, release, local installation and effective resolution stay distinct. Do not repeat complete governance to repair one receipt.
4. Update sourced memory and local Git through exact preserve plans, keeping index/WIP and user rules. No meaningful change means no artificial task, commit or governance version. A file reference does not establish a backup.
5. Run update_check for the chosen official stable/RC channel and explicitly retain an update_assess applicability decision. Network failure is unverified. Installation follows maintenance authorization for a concrete object; do not track development branches or install every release automatically.
6. Inspect selected receipts once, finish the selected run where supported and retain unfinished positions. Report meaningful progress, exceptions or needed action. Waiting is normal retained work, not failure. A completed batch is not project completion.

Report runtime/method identity separately from custom project rules. Next-work suggestions follow the chosen coordination role. Optional remote/cloud work follows explicit destination/scope and existing authorization. Capture, local validation, upload, download and independent restore have separate results. Never treat a synced live state database or active Git metadata as a sealed backup.
