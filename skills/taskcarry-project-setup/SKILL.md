# Project onboarding and maintenance

A first installation follows the three-step [onboarding method](references/onboarding.md). Start from the outer TaskCarry working folder and inspect its `toolkit/` for the complete product entry, package metadata and this method. Keep the extracted version directory. Resolve this locally; do not ask the user to fill in product paths. Ask only about a concrete missing, incomplete or ambiguous package. Reading the toolkit supplies the TaskCarry method, not the user's project contents.

Route existing governance first: installed TaskCarry uses its original governance chat/control and maintenance path; another governance tool needs read-only inheritance and a scoped continuation plan; a governance chat without tools needs its effective decisions and stopping points preserved while filling setup gaps. Do not upgrade, uninstall or migrate another tool as an incidental TaskCarry action. Inspect `identify` before initializing state. Unknown or incompatible state is preserved for review. Reuse verified installations, task identities, decisions and WIP.

Unless the user already selected a project, inventory current permitted host conversation indexes before reading conversation bodies. Use supported native listing or the packaged adapter, paginate active and archived sources separately, and report source/cursor/remaining-page coverage. An exhausted index is only that source's coverage, not all accounts, devices or cloud conversations. Let AI propose project groups from metadata, then ask the user to select a scope before reading related history. Do not infer business identity from a directory or title alone.

Retain the inventory, AI candidate groups and the user's exact selection with `discovery` plan/execute in the selected governance home, including before control initialization. Read status before resuming. The bounded draft uses `.taskcarry-onboarding/discovery` and does not create a control database. A plan is read-only; execute only the reviewed returned plan. Its receipts are inventory/selection evidence, not history understanding or a native connection. Follow the reference for re-selection and later onboarding mapping.

Default to an independent governance chat for project memory and continuity. Give one initial project assessment and work-division suggestion; ongoing project coordination is the user's choice. A real project may span several directories and existing state sources, and several chats may share one business directory. Keep routing explicit; do not merge stores, duplicate tasks or redefine projects from folder names. Historical reference chats may remain source-only: they need neither MCP in the original window nor a new Git directory.

Standard onboarding uses the explicit `complete_v1` profile: local Git governance saving, portable project identity, understood source revisions, actual task/Git work locations, native MCP acceptance and consumed current entries in each active window, a first bounded governance cycle, a verified recovery set and isolated restore, original-chat report/absorption schedules, and official release checking. Private remotes, cloud storage and additional machines remain optional destinations. These are assistant-led steps. A missing host capability leaves a precise pending step; manual work may continue without claiming complete configuration or a naturally exercised loop. Legacy readiness receipts retain their original scope.

Use a dedicated installed runtime with isolated startup: `<fixed-python> -I -X utf8 -m taskcarry --project <control> ...`. Explicit source setup is a development connection. `doctor` describes the current process location and disk content; another process must be checked separately.

Group active chats by verified actual working directory and reuse one directory's MCP and Skills. Do not require a new folder or chat for every task. Preserve each chat's original task identity. Suggest a separate Git worktree only when concurrent writes need isolation; distinct responsibilities alone do not require separate repositories. For an active chat not attached to a project, first check the actual cwd and supported association with that same directory. A projectless label alone says nothing about available MCP: hosts may supply it through project or user configuration or a plugin. Inspect actual tools without changing user-level configuration. Preserve the original chat/history and give one concrete host action when association, trust or loading is missing.

Preview `setup` before `mode: install`. For a shared directory use `binding_mode: "directory"` with `target` and `workspace`, omitting `task_id`; the connection belongs to the registered real Git directory, not one task. Keep the default task binding for an existing single-task setup, supplying `target`, `workspace` and `task_id` together. Keep `--project` bound to the proper control. Setup installs four Skills and their Markdown references plus a pinned MCP fragment. Plan `connect` with the same binding mode, then execute only its exact saved `plan_id`, preserving unrelated settings. Review conflicts instead of overwriting user edits. Neither command changes host trust, permissions or a chat's cwd.

Publish shared-directory navigation with `workbench plan` using `routing: "shared"` and exact per-chat targets. In each chat, use its verified host `thread_id` to select `workbench status`, then check the returned original task and current view. Never choose the first route or another task when the chat is unknown. Retain a separate reviewed `consume` receipt for every chat; one shared configuration or one successful connection does not prove all chats read the current memory.

Use `onboarding` for the selected scope, actual evidence and next missing action. `schedule_plan` prepares one report slot and one or two absorption slots; the host creates/reuses these original-chat schedules. Do not edit scheduler files or silently create a system job. Record configuration, natural trigger, original AI execution and actual delivery separately. Reuse matching schedules; do not multiply writers.

Include the [official Core maintenance procedure](../taskcarry-governance-reconcile/references/daily-governance.md#official-core-updates-and-user-approved-maintenance) in the project's effective governance rules read by the original schedule. It checks the chosen release channel, assesses project usefulness, prepares a concrete preservation/reload/rollback plan, and asks about the exact maintenance before installation. Preserve deferrals and unchanged-candidate silence. Keep generated schedule prompt hashes exact; adopting an online rule is not evidence that old package/Skill bytes or host configuration changed.

Prepare a filled-in connection card for every selected active chat: original chat, real working location, responsibility/task, governance source, complete activation prompt and expected receipt. Reuse directory setup while checking each chat's own binding and consumption. Suggest additional roles only where useful; there is no required chat count. When a host action is unavailable, give one exact destination, filled-in content, expected result and resume instruction. Existing chats remain in use; restarting the app does not itself establish directory trust. Never substitute governance's MCP result for another window's acceptance. Continue only the missing step. Removal uses setup uninstall and retains modified files, project data and separately activated configuration.
