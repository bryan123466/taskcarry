# Project setup / 项目接入

Use the user's existing local AI host; no separate model server is required. Read [the onboarding method](references/onboarding.md) for project understanding, the resumable checklist and the first review. The primary case is a project already advancing in one or more Codex chats. Default to a new independent governance chat for governance and project memory. Reuse a verified existing TaskCarry governance chat and control instead of creating another. Preserve original work chats, task identities, decisions, files and WIP. Other hosts require their own configuration and instruction-loading verification.

Give a one-time project assessment and work-division suggestion during onboarding. Ongoing project coordination is optional; a suggestion alone does not authorize permanent scheduling or messages to other chats. Users can continue directly in professional chats. Recommend additional chats from actual independent outputs, write ownership and dependencies; zero additional specialists is valid. A new governance directory does not make the business project new.

Start with the fixed installed interpreter: `python -I -X utf8 -m taskcarry --project <control> setup --json '{"mode":"preview"}'`. Inspect the proposed files and conflicts before `mode: install` within onboarding authorization. The default target is control. To bind a registered workbench, supply `target`, `workspace` and `task_id` together in setup JSON; target must match the registered workspace and its actual Git identity, and the task must already exist in that control. Review the intended task/workbench relationship from evidence; the engine does not require a one-to-one assignment. Keep `--project` bound to the original control. Setup validates existing registrations; it does not create them or initialize another store. Distinct governance scopes can use an explicit `server_name`.

Setup creates four local Skills with their Markdown references and `.taskcarry/codex.mcp.toml`; workbench setup also generates `.taskcarry/workbench.json` and `workbench.md`. It does not activate the fragment, edit live configuration or create a chat. Preserve existing `AGENTS.md`, MCP services and user configuration. Explicitly read installed Skills when the host has not discovered them. The workbench files are connection instructions, not another task database.

Use `init` only when creating this project's governance state, then `doctor` to inspect prerequisites. Git is needed only for Git operations, not ordinary file checkpoints. The fixed project used to launch MCP must match the intended governance project. `taskcarry_workspace` registers Git workspaces; it does not create chats or authorize reading all repositories. Ordinary document saving needs no fabricated Git delivery. If no prior work exists, the optional product scaffold may establish a new baseline after reviewing its plan; never run it over an existing project.

Read only relevant permitted context and sources, identifying history that is missing. Keep source facts, confirmed decisions, candidate understanding and suggestions distinct. Retain the effective understanding until a sourced correction is confirmed. Save progress in existing project files and task/checkpoint/artifact records, not a second task database. On "continue onboarding", inspect the saved checklist and actual effects, then finish only missing steps.

For each window, distinguish materials generated, host configuration loaded and actual native `taskcarry_doctor` / `taskcarry_status` calls. Record version, interpreter, imported module, control and applicable task/workspace identities. CLI success does not prove native MCP success. If a host action is unavailable, give the single current manual action with its exact destination, filled-in content, expected result and resume instruction. Do not send the user through the entire manual again.

Finish onboarding with one bounded `taskcarry-governance-reconcile` pass in the current chat under its existing authorization. Report inherited work, actual setup, remaining gaps, how to save/continue work and the next step. Empty queues need no sample tasks or deliveries. Reuse this result if scheduling is later requested; installation does not start a schedule. Reports remain normal AI/host chat output, not a separate service.

Keep the installed governance runtime separate from its source checkout. For an installed wheel, invoke its fixed interpreter with `-I -X utf8 -m taskcarry`, including when running setup from a source directory. Generated MCP fragments use isolated UTF-8 startup and explicitly pin the package selected by setup; they fail if that package is unavailable. Setup run explicitly against development source pins that source, so it is a development connection, not an installed governance runtime. Review `doctor.runtime` through the actual host for the imported package and managed setup; it describes this process, not proof that another already-running MCP process loaded the same version. Existing fragments remain unchanged until an authorized setup preview/install update; manually activated host configuration needs separate review and reload. Do not recreate project state during a tool upgrade. A pending setup intent may be resumed by repeating the same install with the same candidate; do not delete the intent or overwrite a changed user file. Multiple independent control stores may use explicit distinct `server_name` values; each still has one receiving baseline.

For removal, `setup` with `mode: uninstall` removes only unchanged managed files. Modified files, governance data and manually activated configuration are retained and reported. Do not remove these by force.
