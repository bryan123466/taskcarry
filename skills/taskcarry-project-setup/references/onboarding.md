# Conversational onboarding and updates

## 1. Establish the governance home

Use the folder the user selected when extracting the complete product ZIP. From that folder, locate the directory containing both `START_HERE.md` and `toolkit/`. Allow for an extra enclosing directory created by the extractor and stay inside the selected folder. For an existing installation, open the original governance chat and use its update route. Keep business workspaces, the dedicated runtime and the governance state distinct from the versioned product files.

Inspect the located package's `toolkit/`, retaining the extracted version directory. Find the complete product entry `START_HERE.md`, `packages/` and package metadata/checksums, and read the installed or bundled onboarding Skill. Do not ask for a product path already determined by this layout; do not present a prompt containing a product-path placeholder. If no complete package or more than one plausible package is present, explain that exact condition and resolve the intended object. Product docs explain how TaskCarry works; project knowledge must come from the subsequently selected user sources.

Classify existing governance before setup: an installed TaskCarry retains the original control/task identity and follows section 4; another tool requires read-only source inspection, scope confirmation and a continuation proposal; a governance conversation without tooling keeps its decisions and unfinished work while standard setup is filled in. Preserve the other system, files and effective instructions. Cross-system migration, deactivation or replacement is a separate concrete action, never an automatic consequence of discovering another governance tool.

Read `identify` at selected locations before `init`. Absent, compatible, unsupported, unknown and corrupt state need different actions. Do not initialize over unknown or later formats. Inspect relevant instructions, actual Git roots/branches/HEAD/index/WIP and existing task records. A new governance folder does not mean a new business project.

Install the bundled wheel using `docs/<language>/manual-setup.md` in the user's verified product directory, checking its exact checksum and preparing a dedicated runtime within onboarding authorization. The installed Skill reference need not share a directory with product docs. Keep isolated startup; a fixed interpreter alone can still import cwd source. Never use an editable installation for governance.

## 2. Understand, inherit and connect

Follow a supplied, clearly selected project scope directly. If the user will choose chats by pasting the invitation, proceed directly to the invitation below. When they want suggestions, list bounded pages of permitted conversation-index metadata first, using currently available native host tools or the supported adapter. Track active and archived scopes separately and follow returned cursors within the agreed limits. Show candidate real-world projects, included chats/directories, grouping reasons and uncertainties. If a bound, unavailable interface or unread page limits coverage, report it and offer the exact continuation. An exhausted index means only the named source/archive scope was exhausted; do not claim all users' conversations, devices, accounts or cloud history were scanned. Directory, repository, chat and project need not map one to one. The user confirms the chosen project before selected history is read.

### Retain discovery before initializing project state

Use `discovery status` to resume the chosen `discovery_id`. Prepare a `discovery plan` with its current `expected_revision` (zero for a new draft), then execute the exact returned plan. This can run before `init` in the explicitly chosen governance working folder: the bounded draft lives under `.taskcarry-onboarding/discovery`; it does not initialize a TaskCarry database or create project/task records. Keep this private local inventory out of public repositories and release packages.

The draft has `sources` containing exact source IDs, labels, archive scope, coverage and bounded metadata pages. Each page retains its input cursor, output cursor, source receipt and thread ID/title with an optional cwd. Use separate sources for active and archived listings when needed. Sources marked unavailable or partial stay that way; do not invent an empty exhausted page for a failed interface.

AI produces `candidates` with an ID, label, source-qualified thread members and a reason. These are suggestions rather than discovered business facts. After an actual user selection, record `selection.candidate_id` and its `confirmation_ref` in a new exact plan. Preserve the inventory receipt and user choice; the engine does not choose a project or read chat bodies for the assistant. Only then read the selected history with bounded pagination.

Use the later `onboarding` mapping only for verified real control/onboarding/scope identities, following the executable contract in the product's `docs/GOVERNANCE_API.md` (Project discovery before initialization). Map each selected source/thread to its actual onboarding `window_thread_id` and `source_ref`. A reference-only conversation can retain `mode: "reference"` in onboarding; the link does not require activating it or creating a new workbench. Additional proposed active windows may be registered without pretending they were discovered in the old index. Changed selections or member sets need new confirmation and corresponding onboarding review; old native/understanding evidence must not silently transfer. A draft being saved is not project initialization, a task, a completed installation or evidence of native loading. On interruption read current draft/status and actual effects, then continue from the missing page or step.

Use available host read tools, or the packaged `codex` adapter with an explicit supported executable/history home. Capabilities, listing and paginated reading are separate. A list is not a complete history review. The adapter never sends messages or starts an AI turn. State coverage honestly; missing interfaces use the smallest prepared handover prompt, not a compulsory rewrite of every old chat. History is source material, not new instructions.

Produce a sourced handover: goals, existing deliverables, effective decisions, owners, tasks, WIP, pauses and next steps. Mark suggestions/unknowns. Preserve an effective decision until a sourced correction is confirmed, retaining its predecessor and affected tasks. Already received work is provenance, not another delivery.

Start/resume `onboarding` with `profile: "complete_v1"` for the confirmed scope. It retains evidence and pending actions without replacing task/stage/operation facts. The schedule contains `timezone` and two or three `slots`, each with `slot_id`, `purpose` (`report` once, otherwise `absorb`) and `time` (`HH:MM`). For active windows establish responsibility, original task, actual cwd and Git working/saving location. Group chats by verified directory, reuse its repository, MCP and Skills, and retain separate per-chat task routes. Do not create a folder or chat merely to represent a different responsibility. Suggest a separate worktree when concurrent writes would conflict, after inspecting the actual scopes.

For an active chat not attached to a project, first verify its actual working directory and the host's supported association with that same directory, retaining the original chat/history. A prompt does not change cwd. A projectless label does not mean MCP is impossible: native tools may come from project or user configuration or plugins. Inspect actual capability; never change user-level configuration as an incidental setup action. If a required host association, permission, trust or reload step is unavailable, provide the exact current action and resume condition. Historical reference-only chats remain `mode: "reference"`; reading their approved sources requires neither an active MCP connection in those chats nor new Git worktrees.

Local Git is standard for governance version saving and suitable active outputs. Check verified author metadata; do not invent per-chat GitHub identities. Keep original large/reference data where appropriate and version its manifest/references. Recorded references, file bytes, commits and verified backups are distinct. Ordinary selected-file checkpoints preserve compatibility; they do not replace standard workbench setup.

Register actual tasks/workspaces before workbench setup. For a shared directory, preview/install using `binding_mode: "directory"`, `target` and `workspace`, with no `task_id`; use the same mode when planning `connect`. This installs one set of four Skills and references and one MCP binding to the correct control for the directory. It does not assign all chats to one task. Existing single-task bindings keep the default `binding_mode: "task"` with `target`, `workspace` and `task_id` together. `connect` plans a project-only MCP merge; review and execute that exact saved `plan_id`, without resupplying target or binding arguments. Preserve other services, comments, settings and AGENTS. Modified same-name unmanaged services require a specific conflict decision. Do not write global Codex configuration. Regenerate machine-specific materials on another machine.

For shared-directory navigation, freeze the selected view and use `workbench plan` with `routing: "shared"`. Each target still names the verified `workspace`, original `task_id` and actual host `thread_id`. The directory's shared `.codex/taskcarry-routing.json` index leads to per-chat current entries retained under the control's `.taskcarry/workbench/chats/`; these are private generated materials. Read `workbench status` with that chat's `thread_id` to select its exact route, and confirm the returned task/source/view before continuing. Unknown or missing chat identities are pending binding work; never fall back to the first route. Record separate reviewed `consume` proof for each chat after it actually reads its entry. A shared directory can share connection files while retaining different task checkpoints and consumption receipts.

For `workbench consume`, pass only `action: "consume"` and `proof`; do not repeat the top-level `routing` selector used for planning/status. The saved plan selects its contract. `proof` requires exactly these nonempty string fields: `workspace`, `plan_id`, `view_id`, `task_id`, `source_id`, `thread_id`, `turn_id`, `evidence_path`, `evidence_sha256`, `reviewer`, `observed_at`. Copy publication identities from the current native status; obtain chat/turn identity from the actual host. After reading the view, retain a bounded review evidence file in an authorized private location **under the control**, use its control-relative `evidence_path` and SHA-256, and state who reviewed what and when. Do not substitute another window's evidence or guess missing IDs. Read status again after consumption. `REVIEWED_EVIDENCE_RECORDED` records the reviewed reference; the separate native calls establish host loading, and the response's `native_acceptance_verified: false` is not changed by this action. The full example is in `docs/GOVERNANCE_API.md` in the verified product directory.

When explicitly converting an existing single-task binding, include its original chat and task in the first shared publication. Preserve the old setup preimages and publication history; adding another chat does not replace that original binding or make an old consumption receipt current again.

Governance prepares one joining prompt for all selected active chats on the same machine. Substitute the verified project name and local control before showing the prompt. For example, ask the recipient to join that project, call its own native TaskCarry tools, match its actual chat to its task, read its current entry and report its responsibility, last saved progress and next action. Use the same text when two chats share a directory. In governance, retain each chat's actual identity, directory, responsibility, task and verification outcome separately. A second paste should reuse the existing registration and current receipt if still valid. If the control differs, the host cannot establish the current chat's identity or several tasks could match, stop binding and give one precise resolution step. A new chat can have its own intended responsibility; ask for it only if it is still unknown. On a different machine use that installation's own control after the user selects the project and exchange scope.

Complete native `doctor` and `status` in each active window. Retain source/control, task/workspace, interpreter/module and checkpoint evidence. CLI and standalone stdio have separate evidence scope. When project configuration is prepared but the existing Windows Codex chat has not loaded the service, give a filled-in host action card: use **Ctrl+O / Open or Add project folder**, select the verified existing directory, and confirm its trust prompt. Associate the original chat with that project using a supported host action, preserving its actual directory and history. Explain that this loads the project's connection configuration; it does not recreate the chat or copy its work. Once all selected directories are configured and trusted, ask the user to **restart Codex once and return to the same original chats** for native verification. A different host may offer an explicit reload instead; follow its actual capability. Configuration and trust alone do not prove a running chat reloaded the service. Do not ask an already verified window to repeat these actions, reinstall the product, or create a replacement chat merely because MCP had not loaded. If the fresh native call still fails, retain its exact error and identify the missing host step before changing configuration.

Check each capability in the environment that will use it. A native read of the local project can proceed while Git saving is pending. For Git-backed saving, check that the actual writer process can locate Git and that the repository has the intended author. If a terminal finds Git and the MCP host does not, report which operation is affected and recheck it from the target host after correction. Git Bash is one possible terminal. Use `preserve` plan/execute for supported repositories and explicit selected files, excluding live state, runtime, secrets and unrelated files. A full local Git-saving result still requires a successful save and readback. Remote backup and collaboration also need an authorized destination and the intended authenticated account. Browser sign-in and commit attribution alone do not verify that account. Coordinate an invitation only when the existing permission is insufficient.

Register `update_source` with official release channel, installed identity and maintenance preference. Run `update_check`, then explicitly retain an `update_assess` decision. Offline means unchecked, not latest. Discovery does not authorize installation. Same version with conflicting bytes requires review. `governance` inspect/record separates runtime/method identity from preserved user-rule fingerprints.

Before declaring setup complete, adopt a portable identity through an exact `identity` plan if this is a legacy control. Record selected source revisions with `cycle` and retain effective facts/decisions with `facts`; listing metadata does not establish understanding. Use `workbench` freeze/plan/execute for shared rules/progress, preserving task identity and professional instructions. Each target needs native verification and separate consumption evidence. Perform a real `recovery` backup/verify and isolated standby restore, including all active workspace payloads and explicitly selected project rules/materials. A checkpoint is only selected-file continuity and cannot substitute for this recovery set.

Use `schedule_plan`, resolve the actual times/time zone if not already given, then create/reuse each native heartbeat attached to this governance chat. Preserve model/permissions. Verify saved chat, directory, period and complete durable prompt. A host lacking native scheduling remains pending; do not substitute a hidden system cron. Use [daily governance](../../taskcarry-governance-reconcile/references/daily-governance.md). Private Git remotes/cloud storage are offered for selected destinations and scope after local setup.

At the end of local setup, tell the user which chats actually joined. If they have not chosen a next step, ask once whether they want to keep working locally, back up selected material to a private repository, invite another AI or computer, or join as a collaborator on another project that already uses TaskCarry. For that last choice, identify the existing manager, confirm the intended project and assigned role through that manager, and reuse its invitation if available. If the project is new to TaskCarry, offer to set up its first manager instead. Follow an already stated choice directly. Two AI tools on the same computer can use the same authorized local project. For a remote route, reuse the selected repository and verified role where available. Confirm the destination and scope before creating a repository or extending access.

### Register the working chat's join receipt

Offer the user a pasteable message even if they skip the suggested list. If the destination project is still unknown, the message asks the working chat to identify the project, its own responsibility and current work for the requesting manager. Treat that as a scope proposal until the project is confirmed. For a known project, the manager fills in the project's persistent source ID, local control and its own verified host chat ID once, then gives the user this invitation:

> Join [project] at [local control] for project manager [manager chat ID]. Check the project identity [project source ID] with your own TaskCarry tools. From this conversation, identify your responsibility, what you have done and what you need next. Reuse your existing task or register your own, verify your working entry, then leave a join receipt the manager can collect. Tell me where I can continue working.

After the invited chat actually reads its exact entry and records its `consume` proof, it writes one UTF-8 JSON receipt under a dedicated, private directory in this control. Give each chat its own path ending in `JOIN_RECEIPT.json`. Record these fields from its verified project, workbench and business context:

| Field | Value |
|---|---|
| `schema`, `project_id`, `control` | `taskcarry.chat-join-receipt.v1`, this project's persistent `source_id`, absolute local governance directory |
| `thread_id`, `workspace`, `task_id` | Actual working chat ID, registered workspace and original task |
| `responsibility`, `business_progress` | Role in this project, plus an object with a short `progress` statement and the actual `waiting_for` or `next_step` from the chat |
| `workbench` | Object with `view_id` and `consumption_id` from the reviewed entry |
| `pending_governance` | Object with `owner_thread` set to the original manager's verified host chat ID and `status` set to `pending_governance_absorption` |

Use `observe` to register the receipt with a stable `observation_id`, a control-relative `source_ref` with forward slashes, SHA-256 of the exact saved bytes as `source_revision`, and this workspace and task. Identify the role and next step in the observation summary. Keep the reference and existing revision when the same proof is valid. Inspect any existing file before updating it and preserve earlier evidence on a substantive correction. If the host cannot establish the chat identity or create a verified project-local receipt, return the concrete missing action. The manager can then help the chat complete its registration.

The manager follows [join intake](../../taskcarry-governance-reconcile/references/daily-governance.md#pick-up-chats-that-joined-this-project). Only the manager can revise the complete project onboarding checklist when its formal scope changes. Keep separate evidence for that checklist, business delivery and acceptance.

### Save evidence without reading implementation code

Read `onboarding status` and its `required` keys. To change one item, call `onboarding` with `action: "update"`, the same `onboarding_id`, current `expected_revision` and an `item` containing exactly `key`, `status`, `evidence`, `next_step`. Status is `verified`, `pending` or `declined`. Every verified item needs a real nonempty `receipt_ref` plus the fields below. Pending/declined items need an evidence object and a concrete nonempty next step; declining a standard item does not complete it. Keep each item within 64 KiB.

| Key | Required additional evidence and source |
|---|---|
| `scope` | `user_confirmed: true`, `scope_fingerprint` copied from the current `onboarding.scope_fingerprint`, after the user confirms that exact scope. |
| `runtime` | `isolated: true`, governance `thread_id`, `transport: "native_mcp"`, `doctor_ok: true`, `status_ok: true`, actual `control`, `version`, `interpreter`, `module_root`, and `identity_ref` to retained runtime evidence. Use native results from that governance chat. |
| `local_git` | Exact `plan_id` and `commit` from the completed `preserve` record. The engine rechecks its `COMPLETED` state and commit. |
| `update_check` | Scope `channel`, `checked: true`, `source: "https://github.com/bryan123466/taskcarry/releases"`, `result_fingerprint` and `assessment_ref`; both last values are the actual saved check fingerprint. |
| `schedule_config` | For `complete_v1`, a `slots` array with every `slot_id` plus governance `thread_id`, selected `time`/`timezone`, `frequency: "daily"`, `readback: true`, `active: true`, `kind: "heartbeat"`, its planned `prompt_sha256`, actual `automation_id`, control as `cwd`, and `runtime_ref`. Read back real native schedules; the plan alone is insufficient. |
| `window:<thread_id>` | Exact scope `thread_id`, `task_id`, `workspace`, `transport: "native_mcp"`, `doctor_ok: true`, `status_ok: true`, actual `cwd`, `control`, and nested `runtime` containing `version`, `interpreter`, `module_root`. Obtain results in that window; cwd must equal its registered Git root. |
| `schedule_trigger:<slot_id>` | Governance `thread_id`, `trigger: "natural_heartbeat"`, `ai_execution_verified: true`, actual `automation_id`, `received_at`, `run_ref`, `update_check_ref`, `local_save_ref`. The report slot also needs `delivered_at` and `delivery_ref`; absorption needs `outcome: "changed"`, `"quiet_no_change"` or `"needs_decision"`. The automation must match this saved slot. |
| `identity` | Actual persistent `source_id` and `replica_id`; a copied directory is not an independently activated writer. |
| `sources` / `first_cycle` | Actual completed `cycle_id` and `coverage_ref`; understood source revisions and current health evidence are checked separately. |
| `workbenches` | One `entries` item per active chat, with exact `workspace`, `task_id`, `thread_id`, `view_id` and `native_doctor_status_verified: true`. Chats sharing a workspace still need distinct entries and reviewed publication, consumption and native receipts. Older workspace-only evidence is usable only when that workspace has one unambiguous selected chat; it cannot attest multiple consumers. |
| `recovery` | Exact `manifest`, `manifest_sha256`, `restore_plan_id`, `restore_receipt_ref` and `restore_verified: true`; verify selected payloads and independent restore effects. |
| `remote` / `cloud` | User-selected `destination` and `coverage_ref` distinguishing actual capture, upload, download and restoration coverage. These two items are optional. |

Pass the exact `update_check` result as `check` to `update_assess`. Its successful response contains `assessment.check_fingerprint`; this equals the check's `fingerprint` and is the assessment's saved key. There is no separate `assessment_id`. Use it for both onboarding `result_fingerprint` and `assessment_ref`, while `receipt_ref` points to retained evidence. An offline/`UNVERIFIED` check remains pending even after recording a `wait` decision. Checking a conflicting or legacy release does not authorize installation.

These are reviewed evidence references, not independent host access. The engine rechecks local workspace/save/update records; it cannot establish chat existence or native loading merely from accepted strings or booleans. Do not synthesize native receipts. A pending thread label is never proof of a real host ID; leave its window pending. Verify governance cwd in the actual host as well. Use the complete field table and executable synthetic start/pending/rebind JSON examples in `docs/COMMANDS.md` in the user's verified product directory; the installed Skill need not sit beside those docs.

### Replace a scope or bind the real chat

An `update` cannot replace `scope`. Before replacing a pending thread label, moving governance to an actual host chat or changing selected windows/channel/schedule, retain the current status report. Call `start` with the **same onboarding ID**, the **current `expected_revision`** and the **complete replacement scope**. This increments the revision and resets current `items` to an empty object; earlier revisions remain in local history. It does not erase task/checkpoint/connection records, move a chat or reinstall files. An identical scope reuses its existing record.

Reconfirm the replacement scope's fingerprint. Review old receipts one by one against the new scope and current bindings. Submit still-valid evidence again with the latest revision after each update; changed chat/cwd/runtime/schedule/channel requires corresponding revalidation. Keep specific gaps pending. Do not bulk-copy old `verified` flags, and do not repeat completed setup or Git effects just because the checklist scope changed. Exact repeated item content is reused. A host-created replacement chat needs its actual identity and original-history references, not a claim that the old chat moved.

### Continue an original task when its chat cannot continue

A chat that repeatedly fails during compaction or cannot open may need a new host chat while its project remains intact. Record the actual host error, last completed turn, outstanding tool operations and the coverage of readable history. Check the original task, checkpoint, current view, saved files and Git state before retrying any work. A failed response does not prove the preceding file or tool action failed. Do not reset project state, reinstall Core, repeat deliveries or restore an old database to repair a conversation.

Prepare a replacement only when needed; an empty spare is not a standard onboarding requirement. A user may choose a pre-created standby for important work, but it must refresh its context before activation. Verify that the original chat and its background operations have stopped writing to the affected scope. If that cannot be established, keep the proposed replacement read-only and state the exact uncertainty. TaskCarry's routing records do not revoke another chat's filesystem permissions or stop its processes.

Give the replacement a filled-in handoff containing the same control/project source, original task and workstream, verified working directory and Git relationship, effective decisions, selected saved outputs, latest checkpoint, last observed effects, outstanding work and history references. Retain the original chat as a source. Explain any unavailable history or unsaved content; do not claim reconstruction of missing conversation context. Creating a new host chat does not create a new business task.

Bind the replacement's **actual** host chat ID. Reuse the original trusted project and directory when appropriate, retaining other configuration. If that directory currently has a single-task binding, use the explicit directory-mode setup/connect and shared workbench publication described above, retaining the original chat/task in the conversion. Publish clear, sourced handoff instructions for both chats: which is now active and what the former chat must read before doing any more work. Review the saved plan before execution. A shared route may retain two chat IDs for the same task; it is not a concurrency lock.

The replacement must perform its own native `doctor`/`status`, read the exact current entry and original task/checkpoint, and record its own consumption evidence. State inherited facts, remaining uncertainty and the one missing action it will continue. Verify an actual useful continuation before calling the handoff successful. If the old chat becomes available again, inspect the current handoff and later effects first; do not let it replay its stale next step. Updating an onboarding scope retains the same onboarding ID and follows the revision/evidence rules above. A replacement governance chat also needs separate review of any original-chat schedule binding; never duplicate a writer or silently copy schedules.

## 3. Verify and recommend next work

Return inherited facts/decisions and uncertainties; a window table of responsibilities, tasks, real directories and actual connections; local version-saving results; original-chat schedule readback; update source/channel/check/assessment; optional backup coverage; and concrete next steps. Every missing standard item stays visible. First natural heartbeat evidence waits for a genuine trigger. One pending window does not erase other completed results.

Users continue in professional chats. Teach “continue my last unfinished task,” “save this stopping point” and “review connected project progress.” Read `context` for task-scoped continuation with source-qualified identities and pagination. Request only changed or missing context. Project memory and initial suggestions are standard; ongoing coordination can change without rebuilding state.

Use one bounded initial governance pass under existing authorization. Empty queues need no fabricated deliveries. Git receive/adopt still needs its real plan and dependency; sharing context or upgrading TaskCarry does not require business merges. For failure, inspect effects and the original operation before retrying. A checkpoint is not delivery; reception is not business acceptance.

## 4. Update an existing installation

Stay in the original governance chat. Inspect runtime, managed methods, selected user-rule fingerprints and pending work. Use the official source and chosen channel. Separate discovery, applicability, preparation, package installation, setup and host loading. The checker never installs. `upgrade` only rebuilds derived indexes.

Choose the smallest applicable change. Documentation-only changes need no runtime switch. For a package change, verify exact artifacts and prepare a separate runtime while retaining the old one. Preview setup, preserve modified Skills/AGENTS and decisions, resolve concrete conflicts, install the selected materials and plan the project configuration merge. Reload and check affected native connections. A version number alone proves neither precise package identity nor another process loading it.

Record candidate/package/method fingerprints, custom-rule preservation, actual effects, host evidence and next condition. Reuse identical reviews. Resume only the missing step. Internal project adoption and developer public release are independent; never receive business stages just to maintain the tool. Give the user a concise outcome and current action; keep version history in the release reference.
